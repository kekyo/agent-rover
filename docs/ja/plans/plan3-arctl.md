# arctlの仕様と実装計画

2026年10月3日に合意した、クライアント用の単発操作CLIの仕様を記録する。
調査対象はコミット`2213dfedd2f85642286c6139a419d23ac355c2af`である。
この文書の保存時点では実装に着手していない。

## 1. 目的と合意した方針

既存のagent-rover NPMパッケージに`arctl`を同梱する。
手動デバッグや検証のため、1回の呼び出しで接続、操作、切断を行う。
起動したアプリ、転送したファイル、保存した画像や動画は、そのまま残す。
通信接続や転送・録画に使う内部一時領域は通常どおり解放する。

対象機能はコマンドの起動、ファイルの送受信、スクリーンショット、動画撮影である。
撮影対象の選択を補助するため、ウィンドウ一覧も提供する。
既存APIの複雑なパラメーターをすべてCLIへ公開することは目指さない。
現在実装されている接続先はWindowsであり、X11エージェントの開発は本計画に含めない。

画面全体の指定方法については、`--window`無指定を採用した。
`windows`には個々のウィンドウのIDを表示し、画面全体を表す特別なIDは追加しない。
画面全体用の追加オプションも設けない。
ここでいう画面全体は、エージェントが動作するデスクトップの全モニターを含む仮想画面を指す。
ウィンドウステーション内の複数デスクトップをまとめて撮影する意味ではない。

以下では、この合意を実装できるよう、入力、保存先、失敗時の扱いを具体化する。

## 2. コマンド体系

| コマンド | 動作 |
| --- | --- |
| `arctl launch [options] -- <command> [args...]` | リモートでコマンドを起動する |
| `arctl put [-r] <local> <remote>` | ローカルからリモートへ転送する |
| `arctl get [-r] <remote> <local>` | リモートからローカルへ転送する |
| `arctl screenshot <output.png> [--window ID]` | 現在の画面をPNGで保存する |
| `arctl record <output.mp4> --seconds N [--window ID] [--fps N]` | 指定時間の動画をMP4で保存する |
| `arctl windows` | 表示中のトップレベルウィンドウを一覧する |

接続設定などの共通オプションは、サブコマンドの前後で受け付ける。
`launch`の`--`以降は、リモートコマンドとその引数として扱う。
その位置より後にある`--help`や`--host`も、arctlのオプションとして解釈しない。

`--help`は全体または各サブコマンドの使用方法を表示する。
`--version`は配布パッケージのバージョンを表示する。
ヘルプとバージョンの表示には接続設定を要求せず、ネットワークへ接続しない。
未知のオプション、引数の不足、余分な位置引数、値の不正は接続前に検出する。

## 3. 接続と共通の出力

### 3.1. 接続設定

| オプション | 環境変数 | 既定値と条件 |
| --- | --- | --- |
| `--host` | `AGENT_ROVER_HOST` | どちらかで指定必須 |
| `--port` | `AGENT_ROVER_PORT` | `39397`。1〜65535の整数 |
| `--token` | `AGENT_ROVER_AUTH_TOKEN` | 認証が必要な接続先では指定必須 |
| `--timeout` | なし | 秒単位で既定30秒。正の有限値 |

明示したオプションを環境変数より優先する。
明示した値が不正な場合は、環境変数へ戻さずエラーにする。
認証は既存の接続処理を使い、認証不要のエージェントではトークンを省略できる。
トークンを結果、進行表示、エラーの説明へ出力しない。

`--timeout`は接続と個々の通信待ちに適用する。
コマンド全体の実行時間や録画時間の上限とは区別する。
秒をSDKのミリ秒へ変換し、録画時間そのものを通信タイムアウトとして扱わない。
エージェントが持つ操作期限や転送容量の上限は、CLIから変更しない。

### 3.2. 結果表示と終了コード

通常は短いテキストで結果を表示する。
標準出力は操作結果に使い、進行状況とエラーは標準エラーへ出す。
CLIのヘルプとメッセージは、既存のコード内文字列に合わせて英語で記述する。

`--json`では、成功結果を1個のJSON値として標準出力へ出す。
最上位に`command`と`result`を持ち、`result`には通常表示と同じ結果情報を含める。
進行表示をJSONへ混ぜない。失敗時の標準出力は空にし、標準エラーへ原因を表示する。
起動結果にはPIDとプロセス名、転送結果には転送元・転送先と件数・バイト数を含める。
撮影結果には保存先と取得できた撮影メタデータ、一覧結果には各ウィンドウの情報を含める。

| 終了コード | 意味 |
| --- | --- |
| `0` | 要求した操作が成功した |
| `1` | 接続、認証、リモート操作、ローカル保存などが失敗した |
| `2` | コマンド構文や引数が不正だった |
| `130` | Ctrl+Cで中断した |

通信断や期限切れで操作の成否を確認できなかった場合は、結果が不明であることを報告する。
起動や書き込みが既に完了している可能性があるため、接続し直して同じ操作を自動再実行しない。
失敗や中断の前に完了した操作を取り消さず、起動済みのアプリや転送済みのファイルを残す。
内部一時領域の解放に失敗した場合も、利用者のファイルを代わりに削除する処置は行わない。

## 4. コマンド起動

`launch`は`applications.launch()`でアプリを起動する。
起動応答を受け取ったらPIDとプロセス名を表示し、接続を閉じて終了する。
終了コード0はプロセスの起動成功を意味し、アプリの準備完了や実行結果までは示さない。
起動したアプリは、CLIの終了、中断、通信切断を理由に終了させない。

| オプション | 内容 |
| --- | --- |
| `--cwd <directory>` | リモートの作業ディレクトリ |
| `--env KEY=VALUE` | 子プロセスの環境変数を追加・上書きする。繰り返し指定可能 |
| `--stdout <remote-file>` | 標準出力を書き込むリモートファイル |
| `--stderr <remote-file>` | 標準エラーを書き込むリモートファイル |

`--env`は最初の`=`で名前と値を分け、空の値も受け付ける。
環境変数名が空の場合は引数エラーとし、同じ名前の指定は後の値を採用する。
ログの保存先にはリモート側のパスを指定する。
リダイレクトの書き込み方や省略時の標準ハンドルは、既存の起動APIに従う。
ログファイルの内容をCLIへ継続転送しない。

実行ファイル名と引数は分けて渡す。
CLIはコマンド全体を独自に連結してシェルへ渡さない。
パイプ、リダイレクト、シェル組み込みコマンドが必要な場合は、利用者が`cmd.exe`や`powershell.exe`を明示する。
シェルのコマンド文字列を指定する場合も、クライアント側のシェルで適切に引用する。

初版には、終了待ち、アプリの終了コードの伝播、対話的な標準入出力の中継を含めない。
起動後のログは`get`で回収できる。

## 5. ファイルの送受信

`put`と`get`では、転送元と転送先の両方を必須とする。
単一ファイルの転送では、転送先にファイル名まで指定する。
転送先がディレクトリだった場合に、転送元のファイル名を自動で付け足す解釈はしない。
同名のファイルは上書きし、必要な親ディレクトリは作成する。

`-r`は転送元ディレクトリの内容を、指定した転送先ディレクトリへ再帰コピーする。
転送元ディレクトリ自身の名前を、転送先の末尾へ自動で追加しない。
空ディレクトリも作成する。末尾の区切り文字の有無でコピー範囲を変えない。
`-r`なしでディレクトリを指定した場合や、`-r`で単一ファイルを指定した場合はエラーにする。

転送先だけに存在する項目は保持する。
同じ相対パスでファイルとディレクトリの型が衝突した場合は、その項目を削除せずエラーにする。
その時点までに転送できた項目は残し、ディレクトリ全体のロールバックは行わない。
書き込み途中の失敗について、元ファイルの内容を復元できるとは保証しない。
ロックを解除するために関連プロセスを自動終了させる機能は設けない。

ローカルの相対パスは、arctlを実行したディレクトリから解決する。
リモートのパスは接続先で解決し、クライアントOSのパス規則で変換しない。
手動操作の例では、リモートパスに絶対パスを使う。
`launch --cwd`は起動するアプリだけに適用し、別のCLI呼び出しへ引き継がない。

初版ではファイルの内容とディレクトリ構造を転送する。
ACL、時刻、リンクなどの属性の再現、include/exclude指定、差分同期、ミラー削除、再開可能な転送は対象外とする。
既存のファイル転送上限を超えた場合は原因を表示し、エージェントの設定を自動変更しない。

## 6. ウィンドウ一覧と撮影対象

`windows`は、実行時点で表示状態にあるトップレベルウィンドウを一覧する。
ID、PID、プロセス名、タイトルを表示する。対象が0件でも成功とし、空の一覧を返す。
一覧を得るために対象を前面化したり、最小化を解除したりしない。
表示状態の判定には既存APIの`visible`を使い、画面上で遮蔽されていないことまでは保証しない。

現在のWindows実装のIDは、ウィンドウハンドルを文字列化したものである。
一覧のIDを別のCLI呼び出しへ渡せるが、ウィンドウが終了すれば無効になり、OSによって再利用される可能性もある。
タイトルやプロセス名を永続識別子の代わりに使う機能は追加しない。
`--window`指定時はその接続で一覧を取得して対象を解決し、対象が見つからなければエラーにする。
無効なIDを画面全体の撮影へ読み替える処置は行わない。

`--window`を省略した場合は、画面全体の撮影APIを呼び出す。
指定した場合は、対象ウィンドウの表示領域を撮影する。
どちらも、その時点でデスクトップ上に見えているピクセルを撮影する。
ウィンドウを前面化、復元、移動してから撮影する操作は含めない。
対象の手前に別のウィンドウが重なっていれば、その表示も撮影される。
画面外の領域や最小化中の対象については、既存撮影APIのクリップまたはエラーの結果を伝える。

画面全体用の特別なIDを設ける案は採用しない。
既存APIが画面全体と個々のウィンドウを別の対象として提供しているため、指定を省略する方法にそろえる。
初版には矩形、モニター、タイトルの部分一致、正規表現による撮影対象の選択を含めない。

## 7. スクリーンショットと動画

### 7.1. 保存先

画像と動画の保存先は、クライアント側のパスを必須で指定する。
PNGまたはH.264 MP4として保存し、拡張子によって別の形式へ切り替えない。
保存先に既存ファイルがある場合は上書きせずエラーにする。
転送コマンドはファイルを置き換える用途、撮影コマンドは結果を追加保存する用途として、この違いをヘルプに記載する。

CLIは保存先を撮影開始前に検査し、必要な親ディレクトリを作成する。
最終的な保存でも既存ファイルの置換を禁止し、事前検査後に同名ファイルが作成された場合も保護する。
成功結果には保存したローカルパスを含める。

### 7.2. スクリーンショット

`screenshot`は1枚のPNGを保存する。
`--window`無指定では`agent.screenshot()`、指定時は`AppWindow.screenshot()`を使う。
描画の安定待ちや期待画像との比較は行わず、撮影要求が実行された時点の状態を取得する。
JSON結果には保存先、撮影範囲、実際に取得した範囲、クリップの有無を含める。

### 7.3. 動画

`record`は`--seconds`を必須とする。
録画時間は0より大きく600秒以下とし、ミリ秒単位まで表せる値を受け付ける。
FPSは`--fps`で1〜240の整数を指定でき、既定値は60とする。
品質は既存APIの既定値90に固定する。
品質、コーデック、音声などの追加オプションは設けない。

`--window`無指定では`agent.recordVideo()`、指定時は`AppWindow.recordVideo()`を使う。
ウィンドウの録画は位置に追従する既定の`followWindow`を使い、切り替えオプションは設けない。
エンコードする大きさは録画開始時に決まり、移動やサイズ変更時の扱いは既存APIに従う。
画面全体の録画も開始時の撮影範囲を使う。

録画の開始、指定時間の撮影、完成したMP4の転送、ローカル保存までを1回の呼び出しで行う。
保存完了後に成功終了し、JSON結果には保存先とSDKから得た録画メタデータを含める。
対応していない接続先では、録画機能を利用できないことを表示する。
機能一覧に録画があってもエンコードに失敗する場合は、その失敗を成功として扱わない。

Ctrl+Cは録画の中止として扱う。
中断後に残りの録画時間を待ち続けず、接続とCLIが所有する内部資源を解放して終了する。
途中までの動画を再生可能なMP4として保存できるとは保証しない。
保存が完了している成果物を中断処理で削除しない。
別々の呼び出しによる録画開始と停止、無期限録画、ライブ配信は対象外とする。

## 8. 利用例と配布

接続先を環境変数へ設定してから、操作を個別に実行する。
次の例はBashなどのPOSIXシェルを想定する。

```bash
export AGENT_ROVER_HOST=192.0.2.10
export AGENT_ROVER_AUTH_TOKEN='...'

arctl put ./app.exe 'C:\work\app.exe'
arctl launch --cwd 'C:\work' -- 'C:\work\app.exe' --debug
arctl get 'C:\work\result.log' ./result.log

arctl put -r ./runtime 'C:\work\runtime'
arctl get -r 'C:\work\results' ./results

arctl screenshot ./screen.png
arctl record ./screen.mp4 --seconds 10 --fps 30

arctl windows
arctl screenshot ./window.png --window 0x12345
arctl record ./window.mp4 --seconds 10 --window 0x12345
```

ウィンドウIDの例は、実際に`windows`で得た値へ置き換える。
認証トークンの実値を文書やテストの出力へ残さない。

配布は`agent-rover/package.json`の`bin`に`arctl`を追加して行う。
別のNPMパッケージや常駐クライアントは作成しない。
`npm install -D agent-rover`で導入済みのプロジェクトでは、`npx arctl`で実行できるようにする。
グローバルに導入した場合は`arctl`として実行できるようにする。

CLIのエントリーポイントは`dist/arctl.mjs`を想定する。
Node.jsの起動行と実行権限を配布物に含め、npmが生成するWindows用ランチャーでも起動を確認する。
既存のNode.js対象バージョンと、SDKのESM/CJS・型定義の配布を維持する。
バージョン表示にはscrew-upの生成情報を利用し、ソースの固定値だけで配布版を表示しない。
パッケージ作成と公開は区別し、本計画にはNPMやGitHubへの公開を含めない。

CLIは引数の解析、既存APIの呼び出し、結果の表示を分ける。
既存の認証やTCPプロトコルをCLI内に複製しない。
通常の起動には`applications.launch()`を使い、終了時にアプリを止める管理ハンドルを作らない。
録画には保存先を受け取る既存APIを使い、完成した動画の転送処理を再実装しない。

ディレクトリ転送には、既存の`mkdir`、`readdir`、`readFile`、`writeFile`などを組み合わせる。
`syncDirectory()`は既定が`mirror`であり、`update`でも型の衝突時には既存項目を削除する。
削除を伴わないCLIの契約を守るため、初版の`-r`にはこの同期処理をそのまま使わない。
差分同期は要件にないので、CLIに差分判定や同期ポリシーの追加設定を持ち込まない。

現行の録画APIは、開始応答の後に指定時間を待って結果を取得する。
接続を閉じるだけでCLIの時間待ちや転送用一時領域が残らないかを、録画の実装段階で検証する。
必要なSDK内部の変更は、切断・中断に連動する待機終了と所有資源の解放に限定する。
公開APIを広げたり、エージェントの録画開始・停止プロトコルを追加したりしない。

実装にはTypeScript、Vite、Vitest、npmを使う。
引数解析には、実装開始後の利用者の指定に従いcommanderを使う。
既存のprettier-maxとscrew-upを継続し、resolved-killerを含む指定ツールの適用箇所を実装前に確認する。
外部ライブラリのAPIは、公式文書とインストールされた版のAPIコメントの両方で確認する。
必要なパッケージや検証用コマンドが不足している場合は、利用者に導入を促す。
依存コードは変更しない。ビルド時のテキスト処理が必要な場合はfuncityを使う。

## 10. 段階ごとの実装計画

各段階は、追加する動作のテストでREDを確認してから実装する。
対象テストのGREENとビルドを確認し、実行可能なCLIを残してコミットする。
段階ごとにREDとGREENの結果、実行環境、未確認事項を本書へ追記する。
計画と実装が食い違った場合は原因を調べ、仕様を変える必要があれば利用者に確認する。

### 段階1　実行可能なCLIとウィンドウ一覧

成果物は、パッケージに同梱された`arctl`と、接続して使える`windows`である。
引数解析、接続設定、ヘルプ、バージョン、通常出力、JSON出力、終了コードを実装する。
認証と接続は既存SDKを使い、成功時も失敗時も接続を閉じる。
共通のCtrl+C処理を用意し、中断後に新しい操作を開始しない。

ビルド済みCLIを子プロセスで実行し、標準出力、標準エラー、終了コードで検証する。
偽エージェントとのTCP通信で、設定の優先順位、認証、一覧の内容、0件の一覧を確認する。
ヘルプや引数エラーで接続が発生しないこと、JSONに進行表示が混ざらないことも確認する。

完了条件は、`npx arctl windows`相当の呼び出しで一覧を取得でき、接続不要の操作を単独で実行できることである。
既存SDKのビルドを通し、`feat: add arctl entry point and window listing`としてコミットする。

### 段階2　副作用を残すコマンド起動

成果物は、引数、作業ディレクトリ、環境変数、ログ保存先を指定できる`launch`である。

実際の子プロセスで、日本語や空白、引用符を含む引数、作業ディレクトリ、環境変数を観測する。

起動対象の終了を待ってから成功する実装になっていないことも検証する。

### 段階3　単一ファイルとディレクトリの送受信

### 段階5　時間指定の動画撮影と中断
