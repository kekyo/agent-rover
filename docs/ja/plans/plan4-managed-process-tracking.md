# 管理プロセスの終了判定と子孫の識別

2026年11月17日に調査した、管理プロセスの終了待ちと子孫の誤認を修正する計画である。
調査対象はコミット`79f99153973a4ee64426fa8abed9b253cff226be`である。
[muon-uiのplan18](../../../../muon-ui/docs/ja/plans/plan18.md)に記録されたagent-roverの課題を、現在のコードと再現試験で確認した。

修正は終了判定を直す段階と、子孫一覧・ウィンドウの所属判定を直す段階に分ける。
初回保存時点では調査と隔離コピーでの修正案の検証まで完了しており、本体コードへの適用は行っていない。
初回保存後の実装と検証結果は8章に記録する。

## 1. 用語と対象

| 用語 | この計画での意味 |
| --- | --- |
| SDK | 利用者のテストなどからリモート操作を呼び出す、agent-roverのTypeScriptライブラリー |
| エージェント | 操作対象のPCで動き、SDKからの要求を処理するプログラム |
| RPC | SDKとエージェントの間で、メソッド名と引数を送って結果を受け取る通信 |
| PID | OSがプロセスへ割り当てる番号。別のプロセスへ再利用されることがある |
| 管理プロセス | `processes.launchManaged()`で起動し、SDKのハンドルから状態取得、終了待ち、終了、解放を行う対象 |
| 管理ID | エージェントが管理プロセスの資源を識別する番号。OSのPIDとは別に割り当てる |
| ルート | 管理プロセスとして最初に起動したプロセス |
| 子孫 | ルートから起動された子プロセスと、その先の子プロセス |
| Job | Windowsが複数のプロセスをまとめて管理するオブジェクト。現在のnativeエージェントは管理プロセスごとにJobを保持する |
| native管理 | エージェントの`process.launchManaged`を使い、保持されたプロセスハンドルとJobで管理する経路 |
| 非native管理 | `applications.launch`で起動し、SDKがプロセス一覧から子孫を推定する経路 |
| 疑似エージェント | SDKのテストで通信先を代用する`fake-tcp-agent.ts` |

主な修正対象はWindowsのnative管理である。
SDKの公開操作として、`snapshot()`、`waitForExit()`、`processes()`、`windows()`と、それらを利用するウィンドウ待機を扱う。
非native管理は別の実行経路として維持し、native管理の修正によって既存の動作が変わらないことを検証する。

## 2. 確認した問題

### 2.1. 終了済みでも終了待ちが続く

SDKの[管理プロセス処理](../../../agent-rover/src/driver/connection.ts)は`process.managedSnapshot`でルートの状態を取得する。
続いて`process.list`の親PIDと作成時刻から子孫を推定し、`process.managedRunning`でnative側の稼働状態を取得する。
現在の`running`はルート、推定した子孫、native側のいずれかが実行中なら`true`になる。

子孫の推定では、候補の親PIDが追跡中のPIDに含まれ、候補の作成時刻がルート以降なら対象に含める。
作成時刻を取得できない場合も対象に含める。
この比較では、時計が過去へ変更された後にPIDが再利用されると、起動前から存在する別のプロセスを子孫と判定し得る。
一度追跡したPIDもSDK内に保持するため、PIDだけで所属を表す問題が残る。

一方、native側の[ManagedProcessRunning](../../../agents/windows/win32_process.cpp)は、Jobの`ActiveProcesses`から稼働状態を返している。
[通信仕様](../../../agents/README.md#managed-capture-and-tree-state)でも、親が終了した子孫を含むJob全体の状態を返すと定義している。
SDKが推定した子孫の状態を加えることで、native側が終了済みと返しても`waitForExit()`が待機を続ける。

plan18のWindows診断では、PID 5876の対象プログラムは終了コード0で終了していた。
しかし、SDKは既存の`SecurityHealthSystray.exe`、`cmd.exe`、agent自身などを子孫へ含め、全体を実行中と判定していた。
対象プログラムの作成時刻は09時52分台UTC、誤認した既存プロセスの作成時刻は17時台UTCだった。
この診断と、公開API・通信仕様を使った単独試験で、終了判定の不具合を確認した。

### 2.2. 一覧とウィンドウ検索にも誤認が残る

`processes()`は`snapshot().processes`を返す。
`windows()`はルートと推定した子孫のPIDを使い、管理プロセスに関連するウィンドウを探す。
そのため、`running`の集計だけを変更しても、無関係なプロセスやそのウィンドウが結果へ混入する。

隔離コピーにplan18の最小修正を適用し、Jobが終了済みの条件で確認したところ、`waitForExit()`は完了した。
同じ条件でも、無関係なプロセスを`processes()`が返し、起動前から存在するそのウィンドウを`windows()`が返した。
この2件を段階2の再現条件とする。

### 2.3. 疑似エージェントがJobの状態を表していない

[疑似エージェント](../../../agent-rover/tests/helpers/fake-tcp-agent.ts)の`process.managedRunning`は、ルートが実行中かどうかだけを返している。
親の終了後に子孫が残るケースでも`false`を返すため、native側の通信仕様と一致しない。

この状態で最小修正を適用すると、[既存の子孫待機テスト](../../../agent-rover/tests/driver.test.ts)が失敗する。
期待値は維持し、疑似エージェントでJobの所属をプロセス一覧とは別に指定できるようにする。
SDKと同じ親PID・作成時刻の推定をテスト側へ移して、期待する状態を作らない。

### 2.4. 原因が確定していない事象

plan18にはほかのWindows終了待ちの失敗と、通知設定の値を取得できない事象も記録されている。
これらがすべて同じ原因かどうかは未確定である。
通知が表示されても試験操作が完了しない事象の一部では終了待ちの誤判定を確認したが、通知機能全体の不具合を説明したとは扱わない。
修正後の再試験で残る失敗は、取得した診断に基づいて切り分ける。

## 3. 修正方針と範囲

終了判定と所属判定の両方で、native側が保持する管理情報を使う。
作成時刻の比較条件を追加したり、待機期限を延ばしたりすることで、今回の終了待ちを解消する方針にはしない。

| 対象 | 方針 |
| --- | --- |
| native管理の終了待ち | 推定した子孫の状態を`running`の判定から外す |
| native管理の子孫一覧 | Jobに所属するプロセスをnative側で取得し、SDKへ返す |
| ウィンドウの所属判定 | native管理ではJobから得た所属情報を使う |
| 疑似エージェント | Jobの所属と、OS全体のプロセス一覧を別々に指定する |
| 非native管理 | 既存経路を維持し、native管理との分岐を回帰試験で確認する |
| 公開型・通信仕様 | 終了判定と所属情報の意味が実装と一致するように説明する |

現在の`kill()`とnative側の解放はJobを使用している。
今回の修正では正常終了、子孫の終了待ち、出力の取得、`killTreeOnRelease: false`の動作を回帰試験で確認する。
無関係なプロセスを終了させる処置や、試験機の時計変更による回避は行わない。

ウィンドウ検索には明示した検索条件を使って起動後の別プロセスのウィンドウを探す既存の経路もある。
Jobへの所属を正す作業と、この検索方法の廃止を混同しない。
今回の範囲はPIDの誤認によって無関係なウィンドウを所属扱いする問題の修正である。

muon-uiの製品機能、通知設定の操作方式、接続管理や回復機構全体の変更は、この計画に含めない。
外部依存コードは変更しない。

## 4. 実装段階

以降、修正前のコードで再現テストが失敗する確認をRED、修正後にそのテストが成功する確認をGREENと呼ぶ。
各段階でREDからGREENを確認し、動作する単位でコミットする。

### 4.1. 段階1　終了判定と疑似エージェント

最初に、公開APIで終了判定を確認する再現テストを正式なテストへ追加する。
実機の時計やPID再利用の発生頻度に依存せず、通信先が返す状態を固定して次の動作を確認する。

| 条件 | 期待する動作 |
| --- | --- |
| ルートとJobが終了済みで、親PIDが一致する古い別プロセスがいる | `running`は`false`になり、終了待ちが完了する |
| 同じ条件で、別プロセスの作成時刻がルートより未来になっている | 作成時刻の順序に左右されず終了待ちが完了する |
| ルートは終了済みで、Jobに子孫が残っている | `running`は`true`のままで、子孫の終了まで待つ |
| Jobに子孫が残っているが、プロセス一覧には現れない | 一覧が空でも終了済みと判定しない |
| 非native管理を使用する | 既存の終了待ちと解放が動作する |

疑似エージェントではJobの所属を明示して子孫の稼働状態も応答へ含める。
この補正後に、現行SDKで時計とPID再利用の条件が失敗するREDを確認する。
親の終了後も本物の子孫を待つ既存テストは、期待値を弱めずに維持する。

修正ではnative管理の`running`から推定した子孫の状態を外す。
plan18のパッチと隔離コピーで検証した最小変更は、次の集計である。

```ts
running:
  root.running ||
  (options.nativeManaged
    ? nativeRunning
    : trackedProcesses.some((process) => process.running)),
```

この段階では既存RPCを使用でき、native側の通信機能追加を待たずに終了待ちを修正できる。
`processes()`と`windows()`への混入は段階2で修正するため、段階1だけで計画全体の完了とはしない。

完了条件は、上表の再現テストと既存の関連テストがGREENになり、SDKのビルドと型検査が成功することである。
達成後に`fix:`のコミットを作成する。

### 4.2. 段階2　Jobに基づく子孫とウィンドウの識別

段階1のコードに対し、無関係なプロセスとウィンドウが結果へ混入する再現テストを追加し、REDを確認する。
親が終了した本物の子孫を一覧とウィンドウ検索で取得するテストも用意する。

native側には管理IDに対応するJobから所属プロセスを取得して返すRPCを追加する。
RPC名、応答形式、機能一覧と通信バージョンの扱いは、実装開始時に既存の規約と照合して具体化する。
新しい互換性維持層は前提にしない。

所属の取得では`JobObjectBasicProcessIdList`を使い、取得したPIDから開いたプロセスハンドルについて`IsProcessInJob`で所属を再確認する。
PIDの列挙とハンドル取得の間にプロセスが終了し、同じPIDが別のプロセスへ再利用される場合を扱う。
状態の取得にも確認したハンドルを使い、所属確認の後にPIDから別のハンドルを開き直す構成を避ける。
列挙中の増減、取得用バッファーの不足、権限不足などの扱いは既存のエラー処理へ合わせる。
状態を取得できない失敗を、管理対象が存在しない状態として成功応答へ置き換えない。

既存の[Job終了待機](../../../agents/windows/operation_worker.cpp)にも、所属PIDの取得とハンドルによる再確認がある。
この実装を参照し、必要な共有部分だけを整理する。
新しいワーカースレッドや、無期限に繰り返す待機を追加しない。

SDKのnative管理では新しい所属情報を`processes()`と`windows()`へ接続する。
親PID・作成時刻の推定と、過去に追跡したPIDの集合をnative管理の所属判定に使わない。
非native管理で必要な推定処理は残し、変更によって使われなくなったコードだけを削除する。
所属情報と稼働状態の取得時点が異なる場合も、推定したプロセスを追加して状態を補わない。

追加する試験は次のとおりである。

- 親PIDと作成時刻が子孫らしく見える別プロセスを、Jobの所属に含めない。
- 別プロセスのウィンドウを、管理プロセスの所属ウィンドウとして返さない。
- ルートや途中の親が終了しても、Jobに残る本物の子孫とそのウィンドウを取得できる。
- PIDの再利用が所属確認と競合しても、別プロセスの状態を返さない。
- Jobの状態取得に失敗した場合は、終了済みという成功結果を返さない。
- 非native管理と、明示した条件による既存のウィンドウ検索が引き続き動作する。

Windowsのamd64・i686をビルドし、native側とSDKの接続を実際に動かして検証する。
公開型のコメント、通信仕様、利用者向け説明のうち、子孫の識別と終了待ちの説明を実装に合わせて更新する。

完了条件は、誤認を再現するテストがGREENになり、本物の子孫を扱う試験、既存のウィンドウ検索、管理プロセスの終了・解放・出力取得の回帰試験が成功することである。
達成後に`fix:`のコミットを作成する。

## 5. 修正後の全体検証

両段階の完了後に、リポジトリーのルートで`npm test`を実行する。
時間がかかる場合も全体試験を省略せず、ログを保存する。
3分を超える見込みならタイマーを使い、継続監視を一時停止する。
ビルドの警告や試験失敗は原因を調べ、修正に伴う問題と環境上の制約を区別して記録する。

Windows実機ではamd64・i686を確認する。
実機がビジーの場合は接続できるまで待ち、試験本体の終了後は速やかに解放する。
Wine上の成功と、Windows実機上の成功は別に記録する。

その後、修正版agent-roverを使い、muon-uiのplan18で終了待ちが失敗したWindowsのパス、ビルダー、通知、サービスUIの各試験を再実行する。
実行したターゲット、修正版の識別情報、成功・失敗・未実施、診断ログを記録する。
ほかの原因による失敗が残る場合は、今回の修正で解消した事象と分け、すべてが同じ原因だったとは結論しない。
muon-uiの製品コードやテストの期待値を変更して、今回のagent-roverの修正を成功扱いにしない。
