# 切断後の回復と親プロセスによる資源管理

## 依頼と停止地点

2026年10月3日に、遠隔の実PCで動くagent-roverについて、改善案1・2・3の実施を依頼された。
案1は操作の終了とファイル回収の分離、案2は親プロセスによるセッション資源の管理、案3は独立した監視プロセスによる自動復旧である。
案4の出力収集方式の変更は今回の対象に含めない。

実装、Linux上で実施できる全体テスト、amd64／i686の配布物作成を終え、デプロイできる地点で作業を中断する。
実PCへの入替、候補版のリモート起動、npmやGitHubへの公開は行わない。
既存のWindows実機統合試験はデプロイ後の確認項目として明記する。
boxrigのステップ23と最初のウィンドウ復元停止の調査は、その後の再開対象とする。

## 現在の障害と原因調査

対象は0.6.0、コミット`c7cc4e65cb9125796a88089011b670243e71f79c`である。
boxrigの実機試験で`window.show`が停止した後、切断時の一時領域回収が共有違反で失敗した。
操作プロセスは終了していたが、回収成功と終了確認を同じ戻り値で扱うため、デスクトップ操作の実行権を返さなかった。
再接続で最初のデスクトップ要求を待っている間にも操作プロセスを作り、所有情報を受け取る前の取消で処理枠が隔離された。

現行の通常解放はJob内のプロセス数を確認するが、切断時は操作プロセスの終了だけを待って削除へ進む。
出力ハンドルは子プロセスへ継承し、削除を共有しないため、子プロセスの終了途中に回収を始める競合が候補となる。
さらに回収エラーのログは実際の失敗箇所である`error.path`を捨て、一時領域のルートを表示している。
実障害でハンドルを保持したプロセスは未特定である。合成障害での再現と、実障害の原因確定を区別する。

根拠は[操作プロセスの終了と回収](https://github.com/kekyo/agent-rover/blob/0.6.0/agents/windows/operation_worker.cpp#L135)、
[通常のプロセス解放](https://github.com/kekyo/agent-rover/blob/0.6.0/agents/windows/win32_process.cpp#L585)、
[実行権の保持](https://github.com/kekyo/agent-rover/blob/0.6.0/agents/windows/tcp_server.cpp#L301)である。

## 維持する契約

TCPの正常切断、接続エラー、要求期限切れを同じ終了経路へ集める。
終了処理は切断済みのクライアントに依存せず、専用の期限で継続する。
未実行の要求は破棄し、古いセッションの要求を新しいセッションへ再送しない。
対象アプリに既に届いた操作の副作用を取り消したとは報告しない。

所有する操作プロセスが停止したことを確認してから実行権を返す。
終了対象の管理アプリ群も親側から停止・確認できるようにする。
`killTreeOnRelease: false`のアプリを切断だけで終了させない。
所有するプロセス、Job、パイプ、回収待ち領域を明示的に保持し、取消や例外で所有者を失わない。
資源数には上限を設け、未回収ファイルの蓄積が制御・復旧操作を止めないようにする。

ファイルの所有権、volume serialとfile index、reparse pointの検査を維持する。
第三者が所有するハンドルを強制的に閉じる処置や、無関係なアプリの終了は行わない。
I/Oと終了待ちはcardioの非同期処理で実装する。依存ライブラリは変更しない。
既存のWin32対象、配布形式、認証、転送容量の指定を維持する。

## 段階1　削除失敗からの回復

最初に、出力ファイルを試験用プロセスが開いたままウィンドウ操作を停止させ、TCPを切断するテストを追加する。
別接続のデスクトップ操作が完了しないREDを確認する。
操作プロセスの停止と一時領域の回収を分け、停止確認後に実行権と実行枠を返す。
未回収領域は独立した期限付き処理で再試行し、実際の失敗パスと段階を記録する。
操作開始前の所有情報を確実に受け取り、実行権の待機中に切断しても回収できるようにする。

完了条件は、ファイルが開いたままでも別接続が操作でき、ハンドル解放後に所有領域を回収できることである。
待機中の切断を繰り返しても実行枠が減り続けず、未実行の要求が後から実行されないことも検証する。
対象テストと両アーキテクチャのビルドを通してコミットする。

## 段階2　親が資源を所有する

操作プロセスを強制終了しても、親に管理アプリ群の終了と一時領域の回収に必要な情報が残るテストを追加する。
Jobと起動処理を親へ登録してからアプリを実行し、操作プロセスの生死に依存しない停止経路を作る。
一時領域の所有情報も、通常操作を許可する前に親側へ確定する。
通常解放と切断時解放で終了確認の条件をそろえ、取得途中の失敗も回収対象にする。
必要なハンドルの継承範囲と、プロセス終了からファイル回収までの順序を検証する。

完了条件は、操作プロセスの停止・強制終了・起動途中の切断でも、終了対象の子孫プロセスと資源を回収できることである。
継続指定のアプリの動作を維持し、保持ハンドル数と処理枠が反復ごとに増えないことを確認する。
ハンドル残存の再現結果と実障害についての未確定事項を記録し、対象試験のGREEN後にコミットする。

## 段階3　独立した監視と自動復旧

通信・GUIを含むエージェントの進行が止まった場合も、別プロセスが期限を監視する。
正常な長時間操作と無活動をハングと誤認しないよう、イベントループの生存と操作の期限を区別する。
操作系の回復が期限内に終わらない場合やエージェント本体が異常終了した場合は、自動的に再起動する。
再起動時も認証トークンと起動設定を維持する。トークンをログへ出さない。
通常のトレイ終了では監視側も終了し、再起動しない。
短時間の再起動回数を制限し、間隔を空けた再試行と診断記録で再起動ループを扱う。

停止を注入する試験で、クライアントの再接続と実際の操作成功まで確認する。
監視側の停止や起動失敗でも所有プロセスを放置しない。
完了条件は、操作系や本体の停止から自動回復し、正常終了・認証・長時間操作の契約を維持することである。
対象試験と既存のGUI・応答性試験を通してコミットする。

## 段階4　配布前の検証と文書

日本語READMEを原本として利用者向けの回復動作と制約を記述し、英語版と配布版へ反映する。
今回の各段階で観測したREDとGREEN、原因調査の結論、残る実機確認項目を本書へ記録する。
全workspaceのテストを実行する。実PCへ候補版を配置する試験は接続環境変数を外して除外し、その件数を報告する。
amd64／i686をビルドし、既存の配布手順とscrew-upで識別可能な成果物を作る。
配布アーカイブの内容とSHA-256、ビルド元コミット、テスト結果を確認する。

最終完了条件は、案1・2・3の回復試験と実施可能な全体テストの成功、両アーキテクチャの配布物、更新した利用者文書である。
この条件と比較して結果を報告し、実PCへのデプロイ前に作業を中断する。
Windows実機でのハング・再起動・デスクトップ操作の最終確認を未実施のまま成功扱いにしない。

## 段階1の検証結果

Wine上で、キャプチャーファイルを別プロセスが開いたままTCPを切断する試験を追加した。
変更前は、次の接続の`clipboard.readText`がタイムアウトした。
停止確認とファイル回収を分離した後は、ハンドルが開いていても操作でき、解放後にファイルを回収できた。
待機中の接続を12回切断しても操作を継続でき、待機していたアプリが後から起動されないことを確認した。
回復試験、GUI試験、複数接続の応答性試験の計3件と、amd64／i686のビルドが成功した。

段階2では、管理アプリの起動専用プロセスを、親が所有するJobへ収容してから起動要求を渡す。
アプリは生成時から同じJobへ所属するため、生成とJobへの割当の間に操作プロセスが終了する競合を避けられる。
操作プロセス自体のJobと管理アプリのJobは分け、Jobの入れ子に依存しない。
この構成で、継続指定のアプリと従来のWin32対象を維持する。

## 段階2の検証結果

変更前は、本体を終了しても、停止中の操作プロセスと管理アプリが残った。
子プロセスの終了待ちが失敗するREDを確認した。クライアントの要求も切断ではなくタイムアウトになった。
操作系のJobと管理アプリのJobを親が保持する構成にし、通信ソケットのハンドル継承も明示的に禁止した。

変更後は、操作プロセスと本体のそれぞれの強制終了で、管理アプリと子プロセスが終了した。
継続指定のアプリは動き続け、操作プロセスの停止後は別接続のクリップボード操作も成功した。
正常起動・解放と存在しない実行ファイルの起動を各16回繰り返し、親のハンドル数に累積増加がないことを確認した。
段階1の回復試験を含む3件、既存の解放失敗注入試験のamd64／i686実行、両アーキテクチャのビルドが成功した。

出力ファイルは子孫にも継承され、操作プロセスの終了だけでは子孫の終了確認にならない。
新しい切断処理は、終了対象のJobを停止し、所属プロセスの終了を非同期で確認してからファイル回収へ進む。
実障害で共有違反を起こしたハンドルの所有者は、引き続き未特定である。
通信ソケットの継承経路が存在したことも、実障害のファイルハンドルの所有者を示す証拠ではない。

段階3では、監視側が匿名共有メモリーに回収待ち領域と操作プロセスの識別情報を保持する。
世代とネイティブ識別情報を検証し、本体の再起動後も、古いセッションのファイルを独立して回収する。
共有領域は固定数に制限し、新しいセッションは所有記録の確定前に操作を始めない。

## 段階3での計画の具体化

未回収領域が上限に達したときも、出力保存を使わない操作を続けられる構成にした。
操作プロセスの登録枠8件と、キャプチャー領域の登録枠64件を分ける。
一時領域は必要な操作の直前に確保する。監視側の枠を予約し、ディレクトリーの識別情報を確定してから出力保存を許可する。
これにより、上限到達後の再接続で空ディレクトリーや回収記録が増え続ける経路も防ぐ。

監視側は、起動後30秒、通常時15秒を本体の進行確認期限とする。
本体は、操作期限と切断後10秒の回復期限も確認してから進行を通知する。
本体を終了し、登録済みの操作プロセスも終了を確認してから次の本体を起動する。
PIDだけで判断せず、生成時刻との一致を確認する。
起動回数は直近60秒に3回までに制限する。トレイの終了要求も共有領域へ残す。

通常終了の検証では、段階1で加えた後処理の寿命管理に問題が見つかった。
完了したpromiseを既定のpromiseで置き換えると、新しい未完了処理が残り、イベントループが終了しなかった。
回収処理が所有者を保持する循環をなくし、完了状態を保ったまま終了できる構成へ修正した。
本体の終了コードも検査し、監視側の強制終了によって正常終了試験が成功することを防ぐ。

## 段階3の検証結果

本体の全スレッドを停止する試験を追加した。監視機能を加える前は、60秒待っても再接続できないREDを確認した。
変更後は本体が自動再起動し、同じ認証情報で再接続してクリップボードを操作できた。
転送上限の起動設定も維持され、古い本体で回収を待っていたファイルも、ハンドル解放後に削除できた。
この試験はamd64／i686の両方で成功した。既存のGUI・複数接続の応答性試験を合わせた4件も成功した。

無活動の状態と、期限内の長時間操作をそれぞれ18秒続けても、不要な再起動が起きないことを確認した。
本体の異常終了からも復旧し、トレイの終了では本体と監視側の両方が終了した。
正常終了の修正だけを戻した場合、本体の終了コードを検査する試験が失敗した。修正後は終了コード0となった。
起動回数の制限は、直近60秒の境界と、起動を延期する場合の履歴保持を単体試験で確認した。

操作プロセスの強制終了を失敗させる注入試験でも、監視側が本体を再起動し、操作を復旧できた。
注入用の処理は試験バイナリーだけにリンクする。配布物には含めない。
操作プロセス・本体・監視側のそれぞれを終了した場合も、終了対象のアプリと子孫が停止し、継続指定のアプリは動き続けた。

回収待ちを64接続分まで埋め、新しいキャプチャーが拒否される状態でも、クリップボード操作とプロセス一覧の取得が成功した。
外部ハンドルを解放すると64領域すべてを回収し、新しいキャプチャーを開始できた。
これらはWine上での障害注入による検証であり、Windows実機での確認はデプロイ後に実施する。
実障害のファイルハンドル保持者と、最初の`window.show`停止の原因は未確定である。

## 段階4の検証結果

2026年10月3日に、実機接続用の環境変数を外して全workspaceのテストを実行した。
Windowsエージェントは15ファイル・23件、SDKは25ファイル・142件が成功した。
SDKのWindows実機統合試験は4ファイル・8件、実機を使うサンプルは1ファイル・1件を除外した。
合計は165件成功、9件除外、失敗0件である。SDKのESM／CJSビルドと型検査も成功した。
Windowsエージェントの試験には、両アーキテクチャのビルド、PEの依存API検査、Wineでの回復試験を含む。

段階1のコミットは`af9d90b`、段階2は`abcd2ce`、段階3は`bbd8c28`である。
テストの全出力は`agents/.build/recovery-evidence/full-test.log`に残す。
日本語READMEを原本として回復動作と制約を更新し、英語READMEと配布版にも反映した。

配布物は既存の`npm run pack --workspace agent-rover-windows-agent`で作成する。
最終ビルドではオブジェクトを作り直し、screw-upが生成するバージョンとコミット識別情報を埋め込む。
成果物の確定時に、ZIP内の両実行ファイルと文書、SHA-256、ビルド元コミットを検査する。
その結果と各完了条件との比較を`artifacts/recovery-deployment.json`に記録し、実機へのデプロイ前に中断する。
同ファイルと配布物はローカルの成果物であり、リポジトリーには追加しない。

## デプロイ後に残る確認

Windows実機には、今回作成した配布物をまだ配置しない。
入替後は、認証情報と起動設定、通常のトレイ終了を最初に確認する。
その後、停止したウィンドウ操作中のTCP切断と、開いたままのキャプチャーファイルを使って、別接続からの操作継続と回収を確認する。
本体の停止・異常終了からの再起動、再接続、子孫プロセスの終了、継続指定のアプリの動作も実機で検証する。
32ビット版についても、実Windowsでの起動と回復を確認する。

元の共有違反を再現できた場合は、ログに記録した実際の失敗パスと管理アプリのPIDを使い、保持プロセスを特定する。
切断後に停止すべき子孫、継続指定のアプリ、外部プロセスのどれにハンドルが残るかを調べる。
停止済みプロセスのハンドルを親が保持しているだけで、そのプロセスのファイルハンドルも残るとは判断しない。
`window.show`の停止原因は別に追跡し、boxrigのP2・I4試験はデプロイ後の継続作業とする。
