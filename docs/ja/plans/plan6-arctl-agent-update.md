# plan6　arctl から Windows エージェントを指定バージョンに更新する

`arctl` はテストドライバーと同じ PC で使うコマンドラインツールである。`arctl update` を実行して、選んだ Windows エージェントを GitHub Releases の指定バージョンに切り替える。アップグレードとダウングレードの両方を扱う。遠隔更新に対応しないバージョンへ戻した場合は、次回の更新時に Windows 上で対応版を手動導入する。

2026年11月18日の `develop`（`c779cf2`）と、その時点で公開されていた 0.1.0〜0.10.0 をもとに設計した。第8節に実装と試験の結果を記録する。

## 1. 更新を行う場所

| 担当 | 処理 |
| --- | --- |
| クライアントの `arctl` | 接続先と稼働バージョンを照会し、更新先のリリースを特定する。ダウングレードを判定して必要な確認を行い、ZIP を取得・検証・展開して対象の実行ファイル（EXE）を送る。更新結果を呼び出し元に返す。 |
| 稼働中の Windows エージェント | 認証などの接続設定に従って更新要求を受ける。受信した EXE を検証し、他のテストが使っていない時点で更新を引き受ける。 |
| Windows 側の一時的な補助プログラム | 更新中も動作し、元のエージェントが正常終了した後で EXE を入れ替える。起動結果を確認して今回の `arctl` に返し、終了する。失敗時は更新前の状態に戻す。 |

XP SP2 が標準で備える TLS（HTTPS の通信を保護する仕組み）では、TLS 1.0 と 1.1 を廃止した GitHub に接続できない。既存の XP SP3 試験機には、時計が2002年に設定されていた記録もある。GitHub との HTTPS 通信とサーバー証明書の検証をクライアントで完結させ、Windows との通信には既存のエージェント用プロトコルを使う。[GitHub の TLS 廃止告知](https://github.blog/news-insights/company-news/weak-cryptographic-standards-removed/)・[Microsoft の Schannel 資料](https://learn.microsoft.com/en-us/windows-server/security/windows-authentication/security-support-provider-interface-architecture)・[XP 実機での記録](plan5-agent-configuration-and-installer.md)

当初検討したトレイのバージョン選択画面と ZIP の持ち込みには、端末側での操作が伴う。Windows に TLS ライブラリと認証局の証明書を同梱する案には、それらの更新と時刻管理が必要になる。LAN 内でリリースを配布する案では配布用サーバーの運用が増える。`arctl` ならバージョン選択から結果確認までテストと同じ PC で行える。

対象版のインストーラーを起動する方法は、セットアップ EXE があるリリースに限られる。バージョン別フォルダーから起動する常駐ランチャーや管理用ポートには、過去のリリースを実行中でも次の更新を受け付けられる利点がある。今回の合意では、遠隔更新に未対応のバージョンからの再更新は手動なので、適用時だけ動く補助プログラムで足りる。

## 2. 利用者から見える操作

`--section` はクライアントの設定ファイル `.agent-rover` にある接続先のまとまりを指定する。各呼び出しで選ぶエージェントは1台とする。

```sh
arctl --section windows-xp update
arctl --section windows-xp update 0.10.0
arctl --section windows-xp --json update 0.10.0 --allow-legacy-downgrade
```

| 指定と状態 | 利用者が観測できる結果 |
| --- | --- |
| バージョン指定なし | 接続先、稼働中の製品バージョン、コミット、実行中 EXE のアーキテクチャ、遠隔更新への対応状況を表示する。この照会だけなら GitHub への接続もファイルの転送も不要。 |
| 指定版が現在より新しい | 接続先と変更前後のバージョンを表示し、アップグレードする。 |
| 指定版が現在より古く、遠隔更新に対応 | ダウングレードであることを表示して適用する。その後も `arctl update` を利用できる。 |
| 指定版が現在より古く、遠隔更新に未対応 | 次回は手動更新になることを伝え、下記の確認を経て今回のダウングレードを実行する。 |
| 同じバージョン | ビルドも一致すれば転送も再起動も行わず「変更なし」を返す。同じ番号でビルドが違う場合は、その旨を表示して指定リリースの EXE に切り替える。ビルドの同一性は対象 EXE のハッシュで確認できるようにする。 |

製品バージョンは `0.9.0`、`0.10.0` のような3個の整数を順に比較する。Git コミットを付けた表示用文字列と通信プロトコルのバージョンは、この比較に使わない。指定タグや対象の Windows 配布物が存在しない場合は、実際の接続先と見つからなかったバージョンを示して終了する。`--version` は従来どおりクライアント自身のバージョンを表示する。[現在のコマンド定義](../../../agent-rover/src/cli/arguments.ts)・[配布時のバージョン形式](../../../agents/scripts/pack-windows.ts)

### 2.1. 遠隔更新に未対応の版への確認

警告の条件は、選択したリリースに切り替えた後で遠隔更新を続けられるかどうかで決まる。公開済みの 0.1.0〜0.10.0 はすべて未対応である。今後のリリースは配布時に記録した対応状況から判定する。`xp-test-01` を選んだときの表示例は次のとおりである。

```text
Downgrade xp-test-01 to agent-rover 0.10.0?
This release does not support 'arctl update'.
The next update requires a manual installation on xp-test-01.
Continue? [y/N]
```

- 実際に選んだ端末と対象版を示し、Windows への転送・停止・ファイル変更の前に確認する。対話実行では `y` で続行する。Enter または `n` なら稼働中のエージェントとテストを継続したまま終了する。
- 非対話実行は入力を待たず、承認がなければ非ゼロで終了する。`--allow-legacy-downgrade` は、この条件のダウングレードを呼び出し元が明示して許可するためのオプションとする。`--json` は出力形式だけを選ぶ。
- 承認後は今回の入れ替えと起動確認までを自動で完了する。次回の更新時に利用者は Windows 上でエージェントを終了し、ポータブル版なら更新対応版の EXE を元の場所に配置し、インストーラー版なら同じユーザー・同じインストール先で対応版のセットアップを実行する。起動後は `arctl --section windows-xp update` などで稼働情報を再び照会できる。現在すでに 0.10.0 以前を実行している端末への初回導入も同様である。

標準出力の JSON は既存の `{ command, result }` 形式に合わせる。接続先、変更前・指定・実際の稼働バージョン、更新結果、次回の手動更新の要否を区別できるようにする。適用を受け付けた操作には更新 ID も付ける。`--json` 使用時の進捗、警告、確認文は標準エラーに出し、トークンは出力・ログから除く。[arctl の出力と中断処理](../../../agent-rover/src/arctl.ts)

## 3. 稼働情報の照会と更新先の固定

接続の準備完了を通知する `agent.ready` と、接続中の照会 `agent.capabilities` は現在、同じ `protocolVersion`、`platform`、`features` を返す。両者と、テストドライバーが使う TypeScript ライブラリ（SDK）の公開型に次の情報を追加する。[エージェントの応答](../../../agents/windows/json_protocol.cpp)・[SDK の公開型](../../../agent-rover/src/index.ts)

| 情報 | 値と用途 |
| --- | --- |
| `agentVersion`、`gitCommit` | 稼働中の EXE に `screw-up` が埋め込んだ製品バージョンとコミットを別フィールドで返す。[ビルド時の定義](../../../agents/version.h.in)・[既存のバナー](../../../agents/windows/version_banner.cpp) |
| `architecture` | 稼働中の EXE の `i686` または `amd64`。64 ビット Windows で 32 ビット版を実行中なら `i686` を選ぶ。 |
| 更新プロトコルの世代 | 更新専用の要求・結果をどの形式でやり取りできるかを `features` 等で通知する。公開リリースにも同じ対応情報を記録する。 |

通常の SDK はテスト用の `protocolVersion` が完全一致した後に操作を開始する。0.10.0 は `2026-09-09.1`、調査時の開発版は `2026-11-17.2` である。
更新では既存の接続・認証の後、双方が扱える更新用プロトコルの世代で、稼働情報の照会から適用・結果確認までを行う。この経路で許可するのは更新に関する操作だけとし、通常の SDK の接続判定を保つ。
接続先の準備完了通知から更新機能の欠如が分かった場合は、その場で診断と手動導入の案内を返す。旧版が通知しない製品バージョンは「不明」と表示する。[現行の接続判定](../../../agent-rover/src/driver/connection.ts)・[0.10.0 の通信定義](https://github.com/kekyo/agent-rover/blob/0.10.0/agents/protocol_version.h)

セクション指定では現在、候補を一巡ごとにシャッフルして利用可能な1台を選ぶ。最初に確定したホスト、ポート、接続資格を今回の更新に結び付け、そこから先の確認・転送・再接続・結果照会は同じ端末に限定する。ダウンロード中に稼働ビルドや対象インスタンスが変わったら、先の確認を流用せず状態を返す。複数候補のセクションを別のコマンドでもう一度指定すれば、別の端末が選ばれ得る。特定の1台を継続して操作するときは1候補のセクションまたは既存の明示接続を使える。[セクションの選択処理](../../../agent-rover/src/driver/selection.ts)

## 4. リリースの取得と検証

1. `arctl` が `kekyo/agent-rover` の公開リリースを完全なタグ名で引き、添付ファイル `agent-rover-agent-win32-{version}.zip` を選ぶ。GitHub の `browser_download_url` から証明書を検証して HTTPS で取得し、リダイレクト先にも同じ条件を適用する。ダウンロードした ZIP の長さと SHA-256 を、そのリリースの添付情報にあるサイズと `digest` と照合する。[GitHub Releases API](https://docs.github.com/en/rest/releases/releases#get-a-release-by-tag-name)・[0.10.0 の添付ファイルとハッシュ](https://github.com/kekyo/agent-rover/releases/expanded_assets/0.10.0)
2. 現行の配布処理は ZIP 直下に `agent-i686.exe` と `agent-amd64.exe` を無圧縮で置く。公開済みの 0.10.0 と 0.1.0 の実物は圧縮した EXE を `dist/` 以下に持ち、文書には親ディレクトリを指す名前もある。クライアントが今回必要な EXE のエントリーだけを読み、固定した出力先へ取り出す。旧 ZIP の無関係な文書は展開しない。対象の欠落・重複、展開サイズ超過、Windows 実行ファイルの形式や CPU 種別の不一致は Windows に送る前に検出する。[現行の ZIP 作成処理](../../../agents/scripts/zip.ts)・[0.10.0 の配布スクリプト](https://github.com/kekyo/agent-rover/blob/0.10.0/agents/pack.sh)
3. 新規リリースでは、`npm run pack` がリポジトリ、タグ、コミット、更新プロトコルの世代、CPU ごとの EXE のサイズと SHA-256 を一覧にし、ZIP に同梱する。既存の10リリースについては、公開 ZIP を GitHub の添付情報と照合し、同じ形式の一覧と ZIP の SHA-256 を `arctl` に同梱する。
4. `arctl` は一覧と取り出した EXE を検証し、Windows にはその EXE とバージョン、CPU、サイズ、SHA-256 を送る。既存のバイナリ転送のチャンク順序・長さ・SHA-256・転送上限を利用する。Windows 側は受信した EXE を専用の一時ファイルに置き、実データのサイズと SHA-256 を照合する。ZIP のハッシュはダウンロード、EXE のハッシュは選択・転送・配置したバイナリの確認に使う。検証エラーや転送中断では一時ファイルだけを片付け、稼働中の EXE を維持する。[バイナリ転送の仕様](../../../agents/README.md#binary-transfers)

## 5. Windows での入れ替え、結果通知、復元

### 5.1. 適用の受け付け

更新 ID で、確定した接続先、更新前のビルド、検証した対象 EXE と1回の適用を結び付ける。サーバーは同じ実行元への適用を一つに絞る。同じ ID・内容への再要求では現在の状態か記録済みの結果を返す。別の更新が先に適用された場合は、選択時の状態が変わったことを通知する。更新先パスは Windows 側が稼働中の EXE から決定する。

通常の単一接続モードに加えて複数接続モードを扱う。他のテストやその終了処理が残る間は使用中と通知し、既存の再試行・中断指定に従って同じ端末で待てるようにする。適用を受け付ける時点で、新たなテスト接続と別の更新要求が同時に始まらないようにする。受け付け前に利用者が取り消した場合は準備を片付ける。受け付けた後はクライアントが切断しても Windows 側で適用または復元まで進める。[接続と終了の管理](../../../agents/windows/tcp_server.cpp)

### 5.2. 実行ファイルと設定

現在のサーバー、監視プロセス、ワーカーは同じ EXE を使う。サーバーだけを止めると監視プロセスが再起動する場合があり、インストーラーも使用中の EXE の置換を拒む。現在動いている更新対応版から一時コピーを作り、更新専用モードで補助プログラムとして起動する案を第一候補とする。コピーは対象 EXE と別パスに置き、元のプロセス群の終了に巻き込まれないようにする。これならポータブル版でも配布物を1本取り出せば更新できる。[監視とワーカーの終了](../../../agents/windows/supervisor.cpp)・[インストーラーの入れ替え処理](../../../agents/installer/windows.nsi.fc)・[Windows のジョブ管理](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

1. 書き込み先、更新元の同一性、他のコピーによるファイル使用、インストール登録の所有先を確かめる。配置予定の EXE と退避先は元の EXE と同じボリュームに用意し、元の EXE、登録値、更新 ID と処理の段階を復元できるようにする。
2. 補助プログラムの準備と結果を返す経路が整った後で、既存の `Exit` と同じ正常終了を要求する。対象の監視プロセス、サーバー、ワーカーの終了をハンドルで確認してから入れ替える。同じパスを使用中の別インスタンスは強制終了せず、使用中として扱う。
3. ポータブル版は起動元のファイル名とパスを使う。インストーラー版はユーザー別の `InstallLocation` と実行元が一致する場合にだけ `DisplayVersion` も更新する。INI、ログ、利用者のファイル、ショートカット、サインイン時の起動登録は保持する。管理者への昇格を前提にしない。
4. 元のユーザー、待受先、起動引数、作業ディレクトリと起動設定を考慮して対象版を起動する。対応版への計画的な再起動では、固定トークンと自動生成トークンのどちらでも同じセクションが再接続できるようにする。自動生成値は今回の再起動に限ってプロセス間で引き継ぎ、INI やログには保存しない。通常起動のトークン生成は既存の仕様に従う。[起動設定とトークン生成](../../../agents/windows/main.cpp)
5. 0.10.0 は現在の設定ファイル `.agent-rover-agent.ini` を読まない。ダウングレード時には対象リリースが受け付ける起動引数と現在の待受・認証設定を照合し、利用者に影響する差を確認時に示す。待受や認証を意図せず弱める組み合わせは停止前に理由を返す。旧版がトークンを新しく生成する場合も、今回の完了通知は元の接続資格で受け取れるようにする。[0.10.0 の起動処理](https://github.com/kekyo/agent-rover/blob/0.10.0/agents/windows/main.cpp)

### 5.3. 何をもって更新成功とするか

旧エージェントを終了する前に、補助プログラムと今回の `arctl` の間で結果通知の準備が整ったことを確認する。第一候補は既存の更新用接続を補助プログラムに引き継ぎ、最終結果の通知に使う方式である。元のサーバーがその接続を切断せずに終了でき、更新先が同じポートで待受を開始できることを段階3の Windows 試験で確かめる。この方式なら追加の管理ポートを開く必要はない。[Windows のソケット共有](https://learn.microsoft.com/en-us/windows/win32/winsock/shared-sockets-2)

| 状況 | 結果と復元 |
| --- | --- |
| 指定版が起動した | 配置した EXE が指定版のハッシュと一致し、その起動に属するプロセスが所定の待受を開始したことを確認する。対応版は新しい稼働情報でも照合する。製品バージョンを報告できない旧版は補助プログラムの確認を使い、旧版への適用も今回のコマンドで成功を返す。待受ポートに別プロセスが応答しただけでは成功としない。 |
| 置換、登録、起動、待受確認のいずれかに失敗 | 対象版のプロセスを終了させ、退避した EXE と登録情報を戻す。元の版の起動と待受を確かめ、「更新失敗・元の版に復元」と失敗箇所を返す。復元も完了できない場合はバックアップを保全し、実際に分かっている状態と復元先を通知する。 |
| 最終応答を受け取る前に切断 | `arctl` は同じ端末に、同じ更新 ID で結果を照会する。更新対応版は適用・復元後も直近の結果を参照できるようにする。旧版が稼働し、補助プログラムの結果も取得できない場合は「結果未確認」と更新 ID を返す。切断を根拠に成功を返したり、別の端末に適用をやり直したりしない。 |

退避した EXE は、起動と必要な登録の確認が済んでから片付ける。途中終了の記録が残っていたら、実ファイルと登録値を照合してから回収または復元する。削除対象は当該更新 ID が作成したものに限る。

## 6. 段階ごとの実装と完了条件

各段階は、期待する利用者の操作を示すテストが失敗することを確認し（RED）、実装後に同じテストを成功させて（GREEN）コミットする。各段階で CLI、配布コマンド、または Windows 試験ドライバーから成果を観測できるようにする。外部ライブラリや Windows API の採用時には公式資料と API コメント、XP 向けのビルド条件を確かめる。

### 段階1　接続した端末の稼働情報を表示する

実際の `arctl --section <name> update` と SDK の照会で同じ情報を取得できるところまで作る。試験用の接続先とビルドした Windows エージェントを使い、製品バージョン・コミット・CPU、JSON 出力、更新に未対応の接続先の表示を検証する。複数候補から選ばれた1台を識別でき、照会だけではファイル転送も再起動も発生しないことを完了条件とする。

### 段階2　リリースを検証し、更新の要否と承認を判定する

実際の `npm run pack` で作る配布物と旧形式の ZIP をクライアントの試験ドライバーに渡す。GitHub の添付情報から ZIP の SHA-256 を取得し、展開した EXE のサイズと SHA-256 を配布時の一覧と照合する。CLI から同一ビルドの省略、版番号の大小、同番号の別ビルド、旧版での `y`・Enter・`n`・非対話承認を確認する。完了条件は、正しい EXE とハッシュを選べることと、タグ不在、破損、ハッシュ不一致、エントリーの欠落・重複、異なる CPU、承認なしでは Windows 上の状態が変わらないことである。

### 段階3　Windows 上で入れ替えと復元を実証する

試験専用のパス・ポートで実際のエージェントを起動し、ローカル試験ドライバーから補助プログラムに適用させる。起動する EXE を変え、旧プロセス群の終了、接続の引き継ぎ、新しい待受と最終応答を観測する。同じファイルを別プロセスが使用中、登録失敗、起動失敗、別プロセスによるポート使用も再現する。完了条件は、対象版または復元した元の版が所定のパス・設定で稼働し、そのいずれかをドライバーが識別できること。XP で接続引き継ぎと再待受を両立できない場合は、この段階で通知方式と計画を見直す。

### 段階4　arctl の1回の実行で転送から起動確認まで行う

利用者と同じ `arctl update` で、2つの更新対応バージョン間を往復する。1台が再起動中で同じセクションの別の1台が空いている場合、別のテストが接続中の場合、転送の中断、適用時の同時要求、同じ ID の再送、最終応答の前の切断を試す。最初の1台だけが各更新 ID につき1回更新され、元の接続設定で結果を得られ、失敗・復元・結果未確認を自動化から区別できれば完了とする。

### 段階5　公開旧版への片道更新と配布形態ごとの動作を確認する

更新対応版から公開版 0.10.0 への切り替えを、通常のコマンドと本物のリリース ZIP で行う。拒否した場合の稼働継続、承認した場合の旧版の起動・待受と最終結果、次の遠隔更新での手動導入案内を確認する。試験後は手動の手順で対応版を再導入する。ポータブル版とユーザー別インストーラー版の両方で、日本語・空白を含むパス、INI、自動起動、表示バージョン、アンインストール登録について適用後と復元後の状態を照合する。完了条件は、旧版に今回の成否を問い合わせる必要がなく、Windows を操作するのは次の手動導入時だけであること。

### 段階6　全体試験と利用者向け文書

全体の `npm test` と `npm run pack` を実行し、両アーキテクチャのビルド、公開配布物、警告、全テストの結果を確認する。Wine と PE の検査に加えて、現行 Windows、i686 の XP SP2、amd64 の XP Professional x64 Edition を対象に実行結果を記録する。過去の XP SP3 の試験は新しい更新機能の SP2 試験とは区別する。実機では試験制御に使うエージェントと更新するエージェントを分け、ポートと配置先を隔離する。標準ユーザーで実行し、試験後に残ったプロセス、ファイル、登録を点検して端末を解放する。[既存の実機試験と対象 OS](../building.md)

利用者向けには日本語の README を原本として、コマンド例、1台の選択、旧版への確認、自動化での明示承認、手動で更新対応版へ戻す手順を記載し、英語版と配布ガイドに反映する。通信のフィールドと結果の意味はプロトコル仕様に記録する。利用者が配布版の `arctl` とガイドから同じ操作を再現でき、実行した試験と未実施の環境を区別できることを完了条件とする。[プロトコル仕様](../../../agents/README.md)

## 8. 実施結果（2026年11月18日）

リリースの検証には SHA-256 を採用した。配布者が署名鍵を用意する手順はない。`arctl` は GitHub Releases に掲載された ZIP のハッシュと、取り出した EXE のハッシュを別々に照合する。Windows は転送後と配置後に EXE を確かめる。通常のトークン認証を使う接続では、選択した EXE のハッシュを既存のトークンと更新 ID に結び付ける。認証を無効にした端末で適用できるのは、端末が既にハッシュを持つ公開旧版と稼働中の EXE に限る。

| 試験 | 観測した結果 |
| --- | --- |
| リリースの選択と検証 | 0.1.0〜0.10.0 の公開 ZIP 10個から、i686 と amd64 の EXE 計20本を確認した。新形式の ZIP でも両 CPU の EXE を照合した。タグや EXE の欠落、ZIP や EXE の SHA-256 不一致、CPU の相違、重複したエントリーは転送前に検出した。 |
| CLI と通信 | 旧版の照会、数値順の比較、旧版への対話確認と非対話の承認を検証した。複数候補から選んだ1台が使用中のときは同じ端末で待機した。最終応答を失った場合は同じ端末に更新 ID を問い合わせ、記録がないときは `unconfirmed` を返した。 |
| Wine・インストーラー版 | テスト用にパッケージ化した更新対応版 0.10.32 と 0.10.34 を往復した。同じ版番号でも EXE が異なれば切り替わり、同一の EXE を指定すると元のプロセスが継続した。公開版 0.10.0 へのダウングレード後は、同じユーザー・インストール先で対応版を手動再導入できた。 |
| Wine・障害時の動作 | 転送した EXE のハッシュが一致しない場合と、インストール登録が壊れている場合は、停止前に更新を拒否し、元のプロセスが次の更新を受け付けた。EXE がロックされていた場合と、置換後に別プロセスが待受ポートを使った場合は、元の版で待ち受けを再開して `restored` を返した。各操作後に INI、利用者のファイル、自動起動、アンインストール登録と表示バージョンを照合した。 |
| Wine・転送中断と再起動 | 転送の最初のチャンクで接続を切ると、元のプロセスと EXE がそのまま使えた。適用中の記録を残して起動する試験では、ディスク上の EXE に応じて `applied` または `restored` を記録し、同じフォルダーに置いた利用者のファイルを保持した。 |
| Wine・自動生成トークン | 試験用の値を自動生成トークンとして設定し、更新対応版どうしを往復して同じ値で再接続できることを確認した。0.10.0 にするとトークンが変わり、その場合でも元の接続で完了通知を受け取れた。 |
| Windows 11 amd64 | 管理者権限を使わず、隔離したポータブル版で稼働情報を照会した。承認なしでは元の版が稼働を続け、承認すると補助プログラムが公開版 0.10.0 の起動を通知した。更新対応版を元のパスへ手動で戻し、再び照会できることを確認した。 |
| Windows XP SP3 i686 | 同じ手順で 0.10.0 への切り替え、補助プログラムからの完了通知、手動再導入を確認した。この端末の試験ユーザーでは Administrators の権限が有効だった。両実機で補助 EXE とその作業フォルダーの自動削除も確認した。その後、試験用プロセスを終了し、試験に使った配置先を削除して端末を解放した。 |

`npm test` は Windows エージェントの45件と SDK・CLI の373件、計418件が成功した。実機接続や試験用配布物の指定を要する試験とサンプルの計20件は標準実行の対象外だった。上表のインストーラー版と実機試験は別途実行した。`npm run pack` で Windows の ZIP、ユーザー別インストーラー、`arctl` を含む npm パッケージを生成した。

XP SP2 の i686 と XP Professional x64 Edition は試験機がないため、実機では未検証である。XP の標準ユーザーでの実行も未検証である。両 CPU の PE のインポートを検査し、待受ポートを所有するプロセスの確認に使う `GetExtendedTcpTable` が XP SP2 の API であることを確認した。[Microsoft の対応 OS と API 仕様](https://learn.microsoft.com/en-us/windows/win32/api/iphlpapi/nf-iphlpapi-getextendedtcptable)

実機で使ったのは試験専用の固定トークンである。自動生成トークンを引き継ぐ再起動と、入れ替え中の電源断からの復旧については、実機での試験を行っていない。
