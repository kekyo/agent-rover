# エージェント設定、自動起動、推奨作業ディレクトリとWindowsインストーラー

2026年11月17日に調査した、Windowsエージェントの設定と配布方法を拡張する計画である。
調査対象はコミット`a0b2ff291f1bdccf084ead4e7dad2b52852669b9`である。
今回の成果物はplan5の保存であり、以下の製品機能はまだ実装していない。
NSISについては製品コードとは別の最小スクリプトでビルドと生成物の検査を行った。

## 1. 提案する構成

この計画でSDKとは、テストドライバーが使うTypeScriptライブラリーを指す。
RPCとは、SDKがメソッド名と引数をエージェントへ送り、結果を受け取る通信を指す。
CLIはコマンドラインからの指定を指す。
INIは`[agent]`というセクションと`key=value`の行で設定を記述するファイルとする。
prefixは、一時ディレクトリ名の先頭部分、またはそれを含む絶対パスを指す。
自動起動は、ユーザーがログオンした後のデスクトップ上での起動を指す。

| 項目 | 推奨案 |
| --- | --- |
| 起動設定 | 項目ごとに、コマンドライン、`$HOME/.agent-rover-agent.ini`、組み込みデフォルトの順で決める |
| INIの編集 | トレイに`Open config file`を追加し、関連付けられたアプリケーションで開く |
| 設定の反映 | エージェントを終了して起動し直したときに反映する |
| 自動起動 | トレイの`Start at sign-in`で、現在のユーザーのRunレジストリ登録を切り替える |
| 推奨作業ディレクトリ | `--safe-base-dir <path>`またはINIで指定し、省略時はエージェント側OSの標準一時ディレクトリを使う |
| ディレクトリの通知 | SDKに`agent.files.safeBaseDir()`、通信に`file.safeBaseDir`を追加する |
| 一時ディレクトリの作成 | `agent.files.mkdtemp()`と名前だけのprefix指定では、推奨作業ディレクトリの配下に作る |
| Defenderの除外 | 通常のインストールでは変更せず、対応OSのローカルUIから明示的に選んだ場合だけ追加する案とする |
| 配布 | ZIPを継続し、同じビルドからNSISインストーラーも生成する |
| インストール先 | 現在のユーザーの`$LOCALAPPDATA\Programs\agent-rover`を既定にする |
| 初回インストール | プログラムメニューへ登録する。ログオン時の自動起動登録と、完了直後のエージェント起動は行わない |
| Windows XP | i686はXP SP2以降、amd64はXP Professional x64 Editionを検証対象にする |

「推奨作業ディレクトリ」は、テスト用のファイルを置く場所としてエージェントが通知するパスである。
そのパスがDefenderの除外に登録済みであることや、ファイルが隔離されないことは、この通知APIでは保証しない。
利用者は別のディレクトリでも作業できる。

## 3. INIによる起動設定

### 3.1. 保存場所と形式

保存場所は`$HOME/.agent-rover-agent.ini`に固定する。
Windowsでは、空でない`HOME`があればそれを使い、未設定または空なら現在のユーザープロファイルのルートを使う。
後者は現在のプロセストークンと`GetUserProfileDirectoryW`で取得する。
同APIはWindows 2000以降に対応し、XPでも利用できる。[MicrosoftのAPI資料](https://learn.microsoft.com/en-us/windows/win32/api/userenv/nf-userenv-getuserprofiledirectoryw)
リンク対象に`userenv`を追加する場合は、既存のPE検査でもXP対応の`USERENV.dll`依存を明示して扱う。

`HOME`に相対パスや無効なパスが入っている場合は設定エラーとする。
実行ファイルの隣、カレントディレクトリ、ドライバー用`.agent-rover`を代替の探索先にはしない。
インストーラーも個別のINI配置ルールを持たず、ファイル作成はエージェント側の編集操作へ集約する。
起動元によって`HOME`の環境変数が異なれば読み込む場所も変わるため、実際のINIパスをログビューアーで確認できるようにする。

設定例は次のとおりとする。コメント中のパスは利用者が準備するディレクトリの例である。

```ini
[agent]
host=0.0.0.0
port=39397
connection-mode=single
max-transfer-size=512
no-auth=false
; unsafe-token=replace-with-your-own-token
; safe-base-dir=C:\RoverWork
```

| INIキー | 対応するコマンドライン | 組み込みデフォルト |
| --- | --- | --- |
| `host` | `--host <host>` | `0.0.0.0` |
| `port` | `--port <port>` | `39397` |
| `connection-mode` | `--connection-mode <single\|multiple>` | `single` |
| `max-transfer-size` | `--max-transfer-size <MiB>` | `512` MiB |
| `no-auth` | `-n`、`--no-auth` | `false` |
| `unsafe-token` | `--unsafe-token <token>` | 指定なし。認証有効時は起動時に生成する |
| `safe-base-dir` | `--safe-base-dir <path>` | エージェント側の標準一時ディレクトリ |

`--help`と`-h`は操作指示なのでINI項目にしない。
`--agent-server`などの内部モード、自動起動の登録状態、Defenderの除外状態もINIに混ぜない。

構文は次の範囲に限定する。

- UTF-8はBOMの有無を許容する。XPのメモ帳で保存できるUTF-16LE BOM付きも読み込む。新規テンプレートはUTF-16LE BOM付きで作る。
- CRLFとLF、空行、行頭の空白に続く`;`または`#`のコメントを許容する。
- セクション名とキー名は上表の小文字表記に統一し、未知の名前、キーの重複、`[agent]`の重複はエラーにする。
- 最初の`=`でキーと値を分け、外側の空白を除く。空白を含むパスも1つの値として扱う。
- 値全体を囲む二重引用符は取り除くが、バックスラッシュをエスケープとして解釈しない。行末コメントは扱わず、値中の`;`、`#`、`=`はそのまま保持する。
- `no-auth`は`true`または`false`とする。数値、接続モード、認証トークンはコマンドラインと共通の検証を使う。
- `unsafe-token=`は明示的なトークンなしとする。`host=`や`safe-base-dir=`など、それ以外の空値はエラーにする。
- `%TEMP%`、`$HOME`、`~`のような文字列の展開は行わない。パスには実際の絶対パスを書く。

小さな設定構文として解析と検証を分け、既存のTypeScript製ドライバー用パーサーをC++側へ持ち込まない。
ファイル内容をコマンドライン文字列へ変換して再解析する方法も使わない。

### 3.2. 優先順位とエラー

コマンドラインの解析結果には値と「指定されたかどうか」を保持する。
INIと統合する前にデフォルトを補うと、指定されていないコマンドライン値がINIを上書きしてしまうためである。
通常の項目は指定されたコマンドライン値、INI値、デフォルト値の順で選び、選んだ値を検証する。

INIのファイル欠落だけは正常な状態として扱う。
存在するファイルの読取失敗、文字コード不正、構文エラーは診断を表示し、起動を止める。
構文として正しいINI値をコマンドラインが上書きした場合、その未使用値の値域エラーでは起動を止めない。
選択された値が不正なら、下位の設定やデフォルトへ黙って戻さない。
エラーにはファイル名、行番号、キー名を含め、トークン本文は出さない。
`--help`はINIの不正や欠落にかかわらず使用方法を表示できるようにする。

認証は`no-auth`と`unsafe-token`で1つの動作を指定するため、通常の独立したキーとは別に解決する。

| コマンドライン | INI | 結果 |
| --- | --- | --- |
| `--no-auth` | トークン指定あり | コマンドラインを優先し、認証無効。INIのトークンは使わない |
| `--unsafe-token CLI_TOKEN` | `no-auth=true` | コマンドラインを優先し、指定トークンで認証する |
| 認証指定なし | `no-auth=true`のみ | 認証無効 |
| 認証指定なし | `no-auth=false`とトークン | INIのトークンで認証する |
| 認証指定なし | `no-auth=true`と空でないトークン | 相反するINI設定としてエラー |
| 両方を指定 | 任意 | 現在と同様にエラー |
| 認証指定なし | 認証指定なし、または`no-auth=false`でトークンなし | 認証有効。トークンを生成する |

コマンドラインで認証を指定した場合は、INIの認証設定一式を採用しない。
INIで明示したトークンも、現在の`--unsafe-token`と同様にログビューアーのトークン欄へ表示しない。
自動生成したトークンをINIへ書き戻すこともしない。

### 3.3. 読み込み時点とプロセス間の受け渡し

公開の起動経路で一度だけ設定を読み、監視プロセスが確定値を保持する。
INIパスと推奨作業ディレクトリも絶対パスにして、サーバーと必要なワーカーへ渡す。
`HostConfiguration`の長さ検証と、ワーカー初期化メッセージも合わせて更新する。
内部モードはINIを再読込しない。

この構成なら、障害回復によるサーバー再起動や、新しい接続のワーカー生成でも同じ設定を使える。
利用者がINIを編集しても、その時点で動いている接続の設定は変えない。
反映にはトレイの`Exit`で全体を終了し、起動し直す手順を案内する。

### 3.4. トレイからの編集

`Open config file`は、読み込みに使ったINIパスをshellの`open`動詞で開く。
ファイルがなければ、説明とコメントアウトした設定例を含むテンプレートを排他的に新規作成してから開く。
現在のコマンドライン値や認証トークンをテンプレートへ転記しない。
既存ファイルは書き換えず、不正なINIも利用者が修正できるよう、エラー画面にパスを示す。

関連付けがない場合は失敗を表示し、メモ帳で開く操作を案内する。
パスを`cmd.exe`などのシェルコマンドへ埋め込まず、Win32 APIへファイルパスとして渡す。
shell openのCOM初期化とエラー処理は公式資料に従う。[ShellExecuteExW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shellexecuteexw)

既存のログフォルダ操作と同じく、ファイルI/Oやshell拡張の待ちをGUI・通信の処理へ持ち込まない。
用途を明示した補助プロセスと既存のcardioによる待機を使う。
編集アプリケーションがエージェントの終了と一緒に終了させられないことも確認する。

## 4. 自動起動の方式

### 4.1. 比較

| 方式 | 特徴 | XPと運用上の扱い | 採否 |
| --- | --- | --- | --- |
| 現在のユーザーのスタートアップフォルダにショートカット | 利用者がExplorerで確認・削除でき、作業ディレクトリやアイコンも指定できる | XPでも使える。フォルダ取得、ショートカット作成、外部変更後の状態確認が必要 | 有力な代案 |
| `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` | 現在のユーザーだけを対象にし、値の追加・削除で切り替えられる | XPを含む対象OSで共通に扱いやすい。実行ファイルパスの引用と登録文字列の長さを検証する | 第一候補 |
| タスクスケジューラのログオントリガー | 遅延や条件を細かく指定できる | XPはTask Scheduler 1.0、Vista以降は2.0となり、分岐と登録管理が増える | 今回の要件には採用しない |
| `HKLM`のRunまたはWindowsサービス | 全ユーザーやマシン全体の起動を扱える | 管理者権限やセッションの違いがあり、現在のユーザーのGUIを操作する用途に合わない | 対象外 |

Runはログオンごと、RunOnceは一度限りの実行なので、継続的な自動起動にはRunを使う。
Runのコマンドラインは260文字以内であり、実行順やログオン後すぐの実行は保証されない。[RunとRunOnceの公式資料](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys)
タスクスケジューラのOS別API条件は[Microsoftの開発者向け資料](https://learn.microsoft.com/windows/win32/taskschd)で確認した。

### 4.2. トレイと登録内容

`Start at sign-in`をチェック付きメニューとして追加する。
ONではRunに値名`AgentRover`を登録し、OFFでは自分の実行ファイルを指す同値を削除する。
メニューを開くたびに登録を読み、変更後も読み直して結果を表示する。
失敗時はチェックだけを反転させず、理由を表示する。
INIへ`auto-run=true`などを重ねて保存しない。

登録内容は引用符で囲んだ現在の実行ファイルの絶対パスだけとする。
次回起動の設定はINIから読むため、その場のコマンドライン指定は引き継がない。
この違いをメニュー操作時の説明とREADMEへ記載する。
トークンなどの起動引数をRunへ複製しない。
自動生成トークンは起動ごとに変わるため、継続して同じ認証情報で接続する場合はINIの`unsafe-token`へ固定トークンを指定する。

一ユーザーにつき1つの登録を扱う。
別のZIP展開先やインストール先が登録されている場合は、そのパスを表示して区別する。
ONの操作は現在のコピーへ登録を更新し、OFFとアンインストールは別コピー向けの値を削除しない。
ZIPの実行ファイルを移動した場合には、移動先で再度ONにする手順を案内する。
i686、amd64、32bitのインストーラーで同じ登録を参照するよう、レジストリのビューをそろえて検証する。

Windows側でスタートアップアプリが無効にされている場合、Runへの登録だけで実行が保証されるとは表示しない。
チェックはエージェントによる登録状態を示し、OS側の設定も確認するよう説明する。
非公開の`StartupApproved`の書換えによって有効化を強制しない。

## 5. 推奨作業ディレクトリと一時ディレクトリ

### 5.1. パスの決定

`safe-base-dir`は、エージェントが動くWindows側の絶対パスとする。
ドライブ付きパスまたはUNCパスを受け付け、ドライブ相対パス、ルートだけの相対指定、空文字列は拒否する。
起動時に存在するディレクトリであることを検証し、存在しない場合やファイルを指す場合は設定エラーとする。
利用者が先にディレクトリを作成し、必要に応じてDefenderの除外を設定する運用とする。

省略時は`GetTempPathW`で取得する。
取得したパスも絶対パスに正規化する。
ドライバーが動くLinuxなどの`tmpdir()`は使わない。
同APIはパスの存在やアクセス権を確認しないため、取得後の検証が必要である。[GetTempPathW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-gettemppathw)
書込み権限やディスク容量の問題は、実際の作成時に操作エラーとして返す。
指定先が使えないときに、別の一時ディレクトリへ黙って切り替えない。

### 5.2. 公開APIと通信

次のAPIを追加する。

```ts
/** Returns the suggested absolute workspace base path on the agent machine. */
readonly safeBaseDir: () => Promise<string>;
```

配置先は`RemoteFileSystem`で、呼び出しは`await agent.files.safeBaseDir()`とする。
RPC名は`file.safeBaseDir`、引数はなし、結果は`{ "path": "C:\\RoverWork" }`とする。
既存の認証・セッション開始処理を通った接続だけで利用でき、INI全体や認証情報は返さない。
ディレクトリ取得によってファイル作成やDefender設定の変更は行わない。

サーバーに保持した確定済みのパスを返す。
返答時にINIやネットワーク共有を読み直さず、`agent.capabilities`と同様にワーカーの長い操作に待たされない経路を使う。
SDKでは空でないパス文字列を検証する。
機能一覧に`file.safeBaseDir`を追加し、後述する`file.mkdtemp`の意味変更と合わせてJSONプロトコルバージョンを更新する。
現在はSDKとエージェントがバージョンの完全一致を要求するため、公開型、両側のバージョン定数、疑似エージェント、通信仕様、テストを同じ段階で変更する。
古いエージェント向けの代替経路は追加しない。

### 5.3. mkdtempの動作

推奨作業ディレクトリを毎回取得してパスを組み立てるだけでは、利用者が従来のハードコードされたパスを使い続けやすい。
そのため、通常の`mkdtemp`自体が推奨先を使う設計を採用する。

| 呼び出し | 動作 |
| --- | --- |
| `agent.files.mkdtemp()` | 推奨先の直下に`agent-rover-`と一意な文字列からなるディレクトリを作る |
| `agent.files.mkdtemp('case-')` | 推奨先の直下に`case-`と一意な文字列からなるディレクトリを作る |
| `agent.files.mkdtemp('D:\\OtherWork\\case-')` | 明示した絶対prefixを使う。推奨先以外で作業する選択を認める |
| 空文字列、`..`、パス区切りを含む相対prefix、ドライブ相対prefix | 引数エラーにする |

公開引数だけをoptionalにし、内部関数には`string | undefined`を明示して渡す。
RPCでもprefix省略を扱い、デフォルトの決定とパスの結合はエージェント側で行う。
絶対prefixを指定する場合の親ディレクトリも、あらかじめ存在することを求める。

Node.jsの`mkdtemp`はprefixへ文字列を直接追加するAPIなので、親ディレクトリをそのまま渡すと、その配下に作られるとは限らない。
今回のリモートAPIでは省略・名前だけ・絶対prefixの3通りを明記し、呼び出し側OSのパス区切りに依存させない。[Node.jsのmkdtemp仕様](https://nodejs.org/docs/latest-v20.x/api/fs.html#fspromisesmkdtempprefix-options)

native側では既存の乱数生成処理を使って候補を作り、`CreateDirectoryW`による新規作成に成功した場合だけ、そのパスを返す。
同名のファイルやディレクトリが存在した場合だけ候補を変えて再試行し、権限不足などの別エラーはそのまま返す。
再試行回数には上限を設け、乱数生成失敗もエラーにする。
`PathExists`の結果を根拠に所有を決めたり、既存ディレクトリを成功扱いする`MakeDirectory`で作成したりしない。
`CreateDirectoryW`は既存名と親ディレクトリ欠落を別のエラーとして返す。[MicrosoftのAPI資料](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createdirectoryw)

### 5.4. 所有と後片付け

推奨先の設定はディレクトリの所有権やアクセス権を変更しない。
`files.mkdtemp`の戻り値は利用者が管理し、テスト終了時にその子ディレクトリだけを削除する。
エージェントの切断、終了、アンインストールで推奨先全体を削除しない。

既存の管理プロセス・録画用の`CaptureRoot`は接続専用の所有情報と回復時の削除に使われる。
今回の`safe_base_dir`と同じ変数へ統合せず、公開の作業ディレクトリに管理用の自動削除権限を与えない。
内部のキャプチャ保存先やログ保存先の移動は今回の対象に含めない。

READMEでは`safeBaseDir()`での確認と`mkdtemp('case-')`での作業場所作成を推奨する。
`C:\agent-rover`などを固定した主要な使用例も置き換える。
任意の絶対パスを使うAPIは引き続き選べること、ディレクトリ通知だけではDefender除外にならないことも説明する。

## 6. Microsoft Defenderの除外設定

### 6.1. 公開されている方法

WMIはWindowsの管理設定を操作する公開インターフェイスである。

| 方法 | 確認した内容 | この計画での位置付け |
| --- | --- | --- |
| PowerShellの`Add-MpPreference -ExclusionPath` | 除外パスを追加できる。昇格したPowerShellが必要 | 利用者向けの手動設定手順に使える |
| WMIの`MSFT_MpPreference.Add` | `ExclusionPath`配列を渡せる。公開資料上の最小クライアントはWindows 8.1 | nativeの設定支援UIを作る場合の第一候補 |
| Windows Securityの除外設定画面 | 利用者がフォルダを選んで設定できる | GUIで設定する手順として案内する |
| 組織のIntuneなど | 管理方針によってローカル設定の上書き・制限がある | 管理端末では管理者側で構成する |

根拠は[Add-MpPreference](https://learn.microsoft.com/en-au/powershell/module/defender/add-mppreference?view=windowsserver2022-ps)、[WMIのAddメソッド](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/defender/add-msft-mppreference)、[除外設定の公式手順](https://learn.microsoft.com/en-us/defender-endpoint/microsoft-defender-antivirus-exclusions-configure)である。
今回使うWMIのDefender用プロバイダーはXPには対応しない。

フォルダ除外はその配下のファイルのスキャン範囲を変える。
標準の一時ディレクトリ全体を自動で除外する設計にはしない。
また、組織で保護された除外設定は、管理者権限があっても変更できない場合がある。[除外設定の改ざん防止](https://learn.microsoft.com/en-us/defender-endpoint/tamper-protection-antivirus-exclusions)

### 6.2. 設定支援UIの提案

通常のNSISインストールはユーザー権限で完了させ、Defenderの変更をインストール条件にしない。
自動構成を提供するなら、トレイの`Add workspace to Defender exclusions...`から利用者が明示的に選ぶ方式を推奨する。
このUIは任意の設定手段であり、未使用でもエージェントの全機能を利用できる。

実装する場合は次の動作とする。

1. CLIまたはINIで明示した、存在するローカルの専用ディレクトリだけを候補にする。標準一時ディレクトリへのフォールバック中、UNCパス、ドライブ全体などは自動構成の対象にしない。
2. 対象パスと、その配下がスキャンから除外されることを画面へ表示する。利用者が選択した後、必要な処理だけを行う補助プロセスへ昇格を要求する。
3. 補助プロセスは元のユーザーが選んだ絶対パスを受け取り、Defenderプロバイダーを確認して`MSFT_MpPreference.Add`を呼ぶ。昇格後の別ユーザーのINIを読み直さない。
4. 既存の除外一覧を置き換える`Set`は使わない。対象パスの追加結果を確認し、成功、既に設定済み、利用者によるキャンセル、非対応、権限・管理方針による失敗を区別する。
5. 設定の読出しが制限される環境では、確認できたと装わず、その旨を表示する。管理者による構成の案内を残す。

昇格する補助プロセスはTCPサーバーやリモート操作を起動しない。
リモートドライバー向けにDefender設定変更RPCは追加しない。
PowerShellコマンド文字列へパスを連結する処理や、非公開のレジストリ書換えは使わない。
XP、プロバイダーのないOS、別製品が保護を担当する環境では、この操作を利用不可とし、エージェントの起動には影響させない。

INIの変更やアンインストールに連動して、既存の除外設定を自動削除しない。
以前の作業フォルダを除外から外す手順はREADMEに記載する。
この追加UIの実装は段階5の選択項目とし、基本機能の完成に必要な段階とは分ける。
その判断にかかわらず、公開API、必要権限、XP非対応、手動手順の説明は基本成果物に含める。

## 7. NSISインストーラーとZIP

### 7.1. インストールされる内容

32bitのUnicode NSISインストーラーに、amd64とi686のエージェントを含める。
OSのアーキテクチャを判別し、選択したバイナリーを`$INSTDIR\agent-rover-agent.exe`として配置する。
以後の更新でパスを変えず、Run登録とショートカットが同じ実行ファイルを指し続けるようにする。
ZIPでは従来どおり両アーキテクチャを選んで使えるようにする。

`RequestExecutionLevel user`と`SetShellVarContext current`を指定する。
既定の配置先は`$LOCALAPPDATA\Programs\agent-rover`とし、WindowsやProgram Filesの固定文字列からユーザーパスを組み立てない。
管理者権限を必要とする全ユーザーインストールやサービス登録は追加しない。
NSISの権限、ユーザー別フォルダ、ショートカットの扱いは[公式スクリプト資料](https://nsis.sourceforge.io/Docs/Chapter4.html)に従う。

プログラムメニューの`agent-rover`フォルダに、起動用とアンインストール用のショートカットを置く。
HKCUのアンインストール情報には製品名、バージョン、インストール先、アイコン、引用済みのアンインストールコマンドを登録する。
起動ショートカットに個別の設定値やトークンは埋め込まない。
初回インストールではRunやスタートアップフォルダを変更せず、完了画面からも自動実行しない。
更新インストールでは、利用者が既にONにした同じ配置先の自動起動設定を維持する。

アイコンには既存の[agent-rover.ico](../../../images/agent-rover.ico)を使う。
Modern UI 2の`MUI_ICON`と`MUI_UNICON`、ショートカット、アンインストール表示に適用する。[Modern UI 2の設定資料](https://nsis.sourceforge.io/Docs/Modern%20UI%202/Readme.html)
このICOには16、24、32、48、64、128ピクセルのDIB画像と、256ピクセルのPNG画像が含まれていることを確認した。
素材の表示も目視確認済みである。既存の[アイコンのライセンス表示](../../../images/README.md)も配布物に含める。

### 7.2. 更新とアンインストール

稼働中の配布先の実行ファイルを置き換える必要がある場合は、トレイからの終了を案内して再試行またはキャンセルできるようにする。
同名の別プロセスや、ドライバーが起動した試験対象を一括終了しない。
ファイルが使用中のまま一部だけ更新されることを防ぐため、更新前の確認と失敗時の復元を試験する。
サイレント実行でも、失敗を終了コードで検出できるようにする。

アンインストールでは配布したファイル、ショートカット、自分の配置先を指すRunの値、同じインストールのHKCU登録を削除する。
INI、ログ、推奨作業ディレクトリ、利用者が作った試験データ、Defender除外は残す。
`$INSTDIR`を無条件に再帰削除せず、配布ファイルを削除した後に空のディレクトリだけを削除する。
起動登録とショートカットの対象パスが異なるZIP版へ変わっていれば、それを削除しない。

### 7.3. ビルドへの接続

配布コマンドは既存の`npm run pack --workspace agents`を維持し、ルートの`npm run pack`からも両方を生成する。
作成するファイル名は次のとおりとする。

- `artifacts/agent-rover-agent-win32-{version}.zip`
- `artifacts/agent-rover-agent-win32-{version}-setup.exe`

エージェント2種、LICENSE、配布README、アイコンのライセンス表示を共通の配布対象一覧として管理する。
ZIPは明示した相対名で格納し、親ディレクトリへ遡るエントリーや古い別名の実行ファイルを混入させない。
NSISにも同じビルド結果を渡す。
設定済みのINI、認証トークン、開発環境のログは配布しない。

実際のpackコマンドから共通の配布処理を呼ぶ構成に統一する。
既存の`pack-windows.mjs`の利用可能な処理をTypeScriptへ移し、ViteでNode.js向けに生成して実経路へ接続する。
Vitestも実際のpackコマンドと生成物を検証する。
統合後に使われなくなった旧スクリプトと独立したZIP生成経路は削除する。
`pack.sh`を残す場合も、共通処理を呼ぶだけのスクリプトにする。

バージョンの決定は既存の`screw-up`へ集約し、両配布物とインストーラーの表示を一致させる。
現在の3要素の数値バージョンは`screw-up format`のテンプレート`{version}.0`でNSISの4要素形式へ整形する。
NSISで表現できないタグの形式や数値範囲はビルドエラーにし、黙って切り詰めない。
手書きのバージョンや独自の文字列分割で別の番号を作らない。
テンプレートへの埋め込みが必要なら、既存のscrew-up機能とfuncityを使う。
整形方法は[screw-upのformat仕様](https://github.com/kekyo/screw-up/blob/main/README_ja.md#formatコマンド)と、[NSISのバージョン情報仕様](https://nsis.sourceforge.io/Docs/Chapter4.html)に従う。

Linuxの固定ツールチェーンイメージへNSISと標準プラグインを追加し、パッケージバージョンも固定する。
`prereq.sh`で準備し、通常の配布作成ではネットワークアクセスや自動インストールを行わない。
`makensis`には警告を失敗として扱う設定を使い、NSISの失敗をZIP成功だけで成功扱いにしない。
追加したTypeScriptのビルドと検査は、既存のnpm、Vite、Vitest、prettier-max、resolved-killerの構成に合わせる。

### 7.4. Windows XPの確認状況

NSISの公式資料にはXP対応が記載されている。
NSIS 3のUnicodeインストーラーはWindows 95/98/MEを対象外にするが、XPを対象外にはしていない。[NSISの対応OSとUnicode](https://nsis.sourceforge.io/Docs/Chapter1.html)
したがって、NSISでXP向けインストーラーを作る方針は採用可能と判断する。

今回、ホストにあるNSIS `v3.09-4`で次の確認を行った。

| 確認 | 結果 |
| --- | --- |
| Unicode、ユーザー権限、既存ICO、アンインストーラーを含む最小スクリプト | `makensis -WX`で警告なくビルド成功 |
| アーキテクチャ判定 | 標準`x64.nsh`の`RunningX64`を組み込んだ。ヘッダーの説明とXP向けのAPIフォールバックも確認した |
| 生成したインストーラー | PE32 / i386、Windows GUI、OS・Subsystemの要求バージョンは4.0 |
| 使用する標準`System.dll` | PE32 / i386、OS・Subsystemの要求バージョンは4.0 |
| 代表的な新OS専用APIの必須import | `GetTickCount64`、`InitializeCriticalSectionEx`、`GetThreadId`、`GetDpiForWindow`、`SHGetKnownFolderPath`、`GetTempPath2`、`IsWow64Process2`は検出されなかった |
| XP上での起動・インストール | 未実施。今回の調査ではXPの実行環境を使用していない |

これは最小スクリプトの静的な検査結果であり、製品インストーラーのXP動作確認ではない。
採用する固定NSIS、Modern UI 2、追加プラグイン、実際の製品バイナリーを含む最終成果物で再確認する。
WineやWindows 11で成功してもXP確認の代わりにはしない。

## 8. 実装段階と完了条件

修正前に要求を満たさないテストが失敗する確認をRED、修正後に成功する確認をGREENと呼ぶ。
各段階でREDからGREENを確認し、ビルドできて動作を観測できる単位でコミットする。
外部ライブラリーAPIは実装前に公式資料とAPIコメントの両方を確認し、外部依存コードは変更しない。
機能を削除する場合は削除を確認するテストでRED、削除後のGREENを経て一旦コミットし、確認用テスト自体を削除して整理する。

### 8.1. 段階1　INIと既存オプション

解析・値の統合・検証の再現テストを追加する。
INIなし、部分設定、CLI優先、認証の組合せ、重複・未知キー、読取失敗、両文字コード、日本語・空白を含むパス、helpを検証する。
その後、公開の起動経路に読み込みを接続し、INIだけでポート・接続モード・転送上限を変えて実際に接続する。
内部モードの起動と、監視プロセスによるサーバー再起動が設定ファイルの変化に影響されないことも確認する。

完了条件は、既存の認証・引数テストと新しいテストが成功し、両アーキテクチャをビルドでき、INIだけの設定が通信へ反映されることである。
`feat:`でコミットする。

### 8.2. 段階2　INI編集メニュー

トレイから既存INIを開くテスト、未作成時にテンプレートを作るテスト、既存内容を保持するテストを追加する。
shell openの失敗、関連付けなし、日本語パス、編集中のエージェント終了も検証する。
画像だけで判定せず、開いたファイルのパス、保存した設定、次回起動での動作を確認する。

完了条件は、利用者がトレイからINIを編集して次回起動へ反映でき、編集アプリケーションが終了処理に巻き込まれず、通信とGUIが応答を続けることである。
`feat:`でコミットする。

### 8.3. 段階3　推奨先の通知とmkdtemp

CLI・INI・標準一時ディレクトリの各設定から、SDKで実際のWindowsパスを取得するテストを追加する。
prefix省略、名前だけ、別の絶対prefix、拒否する相対指定、書込み失敗、並行作成を検証する。
競合相手が同名ディレクトリを先に作る条件を再現し、そのディレクトリ内の既存ファイルを触らず、別の新規ディレクトリを返すことを確認する。

nativeの確定値の受け渡し、RPC、機能一覧、SDK、疑似エージェント、通信バージョンをこの段階でそろえる。
実エージェントへ接続し、新しいAPIで取得したパスと`mkdtemp`の戻り値を照合して、ファイル転送・試験対象の起動・後片付けまで動かす。
主要なREADME例もこの時点で新しい公開APIへ更新する。

完了条件は、標準の作成先が推奨先になり、任意の別パスも選べ、並行呼び出しが既存ディレクトリを共有せず、管理用キャプチャの削除権限が変わらないことである。
`feat:`でコミットする。

### 8.4. 段階4　自動起動メニュー

登録なし、ON、OFF、外部での登録変更、別コピーの登録、書込み拒否、空白・日本語を含む実行ファイルパスをテストする。
初期化処理が勝手にRunへ登録しないことも確認する。
チェック表示だけでなく、実際の登録内容と、専用のWindowsテストユーザーでログオン後にINI設定で起動することを検証する。
OFF後のログオンでは起動しないことも確認する。

完了条件は現在のユーザーだけの登録をトレイから切り替えられ、次回起動がINIを使い、異なるコピーの登録を誤って削除しないことである。
`feat:`でコミットする。

### 8.5. 段階5　Defender設定支援の選択項目

公開APIと制約の調査結果、および手動設定・解除の手順は必ず文書化する。
追加UIを実装する場合は、段階3で確定したパス情報を利用する。
プロバイダーなし、既に登録済み、昇格キャンセル、追加失敗、確認不能をまず代替実装で再現し、専用フォルダだけが対象になることを確認する。
API呼び出しと結果読出しは、実際のDefenderがある隔離したWindows環境でも検証する。
既存の除外一覧を保持し、追加した試験用設定だけを検証後に解除する。

追加UIの完了条件は、利用者が指定した専用ディレクトリだけを、ローカルでの明示操作により追加でき、非対応やキャンセルが通常のエージェント動作へ影響しないことである。
文書だけなら`doc:`、UIも実装した場合は`feat:`でコミットする。
追加UIを見送った場合は、その選択を実装結果へ記録し、基本機能の試験を続ける。

### 8.6. 段階6　NSISと実際の配布コマンド

実際のpackコマンドから両配布物が得られるテストを先に追加する。
ZIPの中身の比較だけでなく、展開した実行ファイルの起動と、NSISによるインストール・起動・アンインストールを確認する。
配布コマンドが実行する処理をテストの対象にそろえ、固定ツールチェーンへNSISを追加する。

最初にユーザー単位でインストールしてプログラムメニューから起動できる最小構成を完成させる。
続いて、更新、稼働中のファイル、サイレント実行、設定と試験データの保持を確認する。
各単位でGREENを確認し、配布機能は`feat:`、ツールチェーンや不要経路の整理は`chore:`または`refactor:`でコミットする。

完了条件は、同じバージョン・ビルドのZIPとNSISが生成され、標準ユーザーでインストールでき、初回は自動起動登録も即時起動もなく、両方の配布形態でエージェントを利用できることである。
