## 1. 現時点の判断

接続#145の処理が長時間滞り、後続の接続を処理できなくなった可能性が高いです。
現行サーバーは1接続の処理が終わるまで次の接続を受け付けません。
この構造により、1接続内の待ちがエージェント全体の応答停止に広がります。

最初に処理が止まった原因は未確定です。
有力候補は、従来型コンソールのQuick Editによるログ出力待ちです。
再起動後の実機でもQuick Editが有効でした。
テスト対象ウィンドウへの同期操作待ちも候補として残っています。

後半の認証エラーの連発は、停止中に待たされていた接続を後から処理した結果として説明できます。
この認証エラーを、最初の応答停止やトークン不一致の証拠とは判断していません。
停止時のスレッドスタックとリクエスト単位の記録がないため、最初の待ちが発生した場所までは特定できませんでした。

今回の方針では、エージェントをPEのWindows GUIサブシステムで起動し、コンソールに依存しない構成へ変更します。
これにより、エージェント自身のコンソール選択でログ出力が止まる経路を取り除きます。
Quick EditをConsole APIで無効化する処理は、実装対象外です。

接続受付の直列化、対象アプリへの同期呼び出し、動画終了の無期限待ちはGUI化後も残る問題です。
ログをファイルへ出すだけでも、書き込みを同期実行すれば別の停止経路になります。
GUI化と併せて、受付・通信、操作の実行、ログの保存・表示を、互いの完了を同期的に待たない構造へ改める案です。

## 5. 現行コードから確認できた動作

### 5.1. 接続の処理は直列

[`RunTcpServer()`](../../../agents/windows/tcp_server.cpp#L387)は、次の順に処理します。

```text
accept()
  → 接続受付ログ
  → HandleClient()
  → closesocket()
  → 次のaccept()
```

`HandleClient()`は、その接続が終了するまで認証とリクエスト処理を続けます。
既存接続がアイドル状態で残っているだけでも、次の接続の認証は始まりません。
OS側でTCP接続が成立しても、エージェント側で認証処理が始まるとは限らない構造です。

[`HandleFrame()`](../../../agents/windows/tcp_server.cpp#L207)は、JSONリクエストを処理してから応答を送信します。
Pingへの応答も同じ接続処理ループで扱います。
ウィンドウ操作、ログ出力、通信などでこの処理が止まると、後続の処理も進みません。

### 5.2. クライアントのタイムアウトはサーバーの処理を中断しない

TypeScript側の既定タイムアウトは30,000ミリ秒です。
通常リクエストのタイムアウトでは、[`createPendingRequestTable()`](../../../agent-rover/src/protocol.ts#L655)が待機中のPromiseを失敗させます。
この処理には、Windows側で実行中の操作を中断する仕組みはありません。

[`frame.cpp`](../../../agents/windows/frame.cpp#L46)の受信と送信は、同期的な`recv()`と`send()`を使用します。
調査対象コードには、`SO_RCVTIMEO`や`SO_SNDTIMEO`によるサーバー側の送受信期限設定がありません。
クライアントの待ち時間を短くしても、サーバー内の待ちが同時に解除されるわけではありません。

### 5.3. 認証待ちのタイムアウトはCloseフレームを送る

[`connectRemoteAgent()`](../../../agent-rover/src/driver/connection.ts#L1875)では、ハンドシェイク待ちがタイムアウトすると`HANDSHAKE_FAILED`を返し、transportの`close()`を呼びます。
[`close()`](../../../agent-rover/src/driver/transport.ts#L260)は、TCP接続が開いていればCloseフレームを`socket.end()`で送ります。

サーバー側の[`AuthenticateClient()`](../../../agents/windows/tcp_server.cpp#L180)は、受信フレームの種類とペイロード長を検査します。
認証応答を期待する位置でCloseフレームを受け取ると、`invalid authentication response frame`を返します。

認証ダイジェストの比較は、そのフレーム形式の検査より後です。
ダイジェストが一致しない場合のメッセージは`challenge response mismatch`です。
今回のメッセージは、認証トークンの不一致を直接示していません。

### 5.4. 応答送信失敗の意味と限界

[`HandleFrame()`](../../../agents/windows/tcp_server.cpp#L230)はJSON応答の送信に失敗すると、切断理由を`failed to send JSON response`にします。
長時間待った後、すでに切断したクライアントへ応答を送ろうとした場合にも、この結果になります。

このメッセージだけでは、送信前の処理に時間がかかったのか、送信処理自体で待ったのかは分かりません。
失敗したリクエスト名、リクエストID、具体的なWinsockエラー番号も記録されていません。

## 6. ログ全体を説明する仮説

接続#145で何らかの処理が止まり、その間にクライアントがタイムアウトや再接続を試みたと考えられます。
サーバーが#145を処理している間、後続接続の認証は始まりません。
認証を待ちきれなかったクライアントは、Closeフレームを送ります。

その後、#145の待ちが解除され、サーバーがJSON応答を送ろうとしたものの失敗します。
サーバーは#145を終了して後続接続を順に処理します。
認証応答を期待する位置でCloseフレームを受け取るため、22接続が同じ認証エラーで切断されたという説明です。

この仮説はコードと確認実験に整合します。
ただし、障害時のパケットを記録していないため、#146〜167が実際に送ったフレームを直接確認したわけではありません。

## 7. 最初の停止原因の候補

### 7.1. Quick Editによる同期ログ出力待ち

[`PrintAgentLogEvent()`](../../../agents/windows/agent_log.cpp#L130)は、時刻付きのログ文字列を作った後、`printf()`と`fflush(stdout)`を呼びます。
この出力はリクエストを処理するスレッド上で同期的に行われます。

従来型コンソールでは、文字選択中にコンソールへの書き込みが待機する場合があります。
Microsoftのコンソール実装でも、選択中などのフラグを検査し、書き込みを待機させています。
根拠は[Microsoftの`_stream.cpp`](https://github.com/microsoft/terminal/blob/main/src/host/_stream.cpp#L586)です。

agent-roverの[`process.launchManaged`処理](../../../agents/windows/json_protocol.cpp#L1273)は、プロセス起動ログを出してから応答を返します。
したがって、起動ログの出力が止まると、起動済みであってもクライアントへの応答は送られません。
選択が解除された後に出力と処理が再開し、応答送信に失敗したという流れが考えられます。

ログの時刻はコンソールへの書き込みより前に決まります。
そのため、古い時刻のログ行が残っていることだけでは、その行の出力がすぐ完了したかどうかも判断できません。

現行の[`wmain()`](../../../agents/windows/main.cpp#L26)にはQuick Editを無効化する処理がありません。
再起動後の実機でもQuick Editが有効だったため、この候補を有力と判断しました。
障害時の選択状態と、選択を解除した操作の有無は未確認です。

### 7.2. テスト対象ウィンドウへの同期操作待ち

[`ActivateWindow()`](../../../agents/windows/win32_windows.cpp#L216)は、必要に応じて`ShowWindow()`を呼び、`BringWindowToTop()`と`SetForegroundWindow()`で前面化します。
[`FocusWindowById()`](../../../agents/windows/win32_windows.cpp#L293)は、子ウィンドウへのフォーカス設定で`AttachThreadInput()`と`SetFocus()`を使用します。
トップレベルウィンドウの場合は、その入力キュー結合の分岐に入りません。

表示状態の変更にも同期的な`ShowWindow()`を使用します。
位置と大きさの変更は[`MoveWindowPhysical()`](../../../agents/windows/win32_window_bounds.cpp#L145)から`MoveWindow()`を呼びます。
これらの処理が対象アプリの応答待ちになると、同じスレッドの通信処理も止まる可能性があります。

Microsoftは、入力キューを結合した後の前面化でハングする事例を説明しています。
また、`SetFocus()`はフォーカス変更のメッセージを送ります。
`ShowWindowAsync()`の説明にも、応答しないアプリの表示処理を待って呼び出し元まで応答しなくなる問題が記載されています。
参照先は次のとおりです。

- [入力キュー結合の危険性](https://devblogs.microsoft.com/oldnewthing/20080801-00/?p=21393)
- [SetFocus](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setfocus)
- [ShowWindowAsync](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showwindowasync)

`focus-peer.exe`の起動直後にログの空白が始まるため、フォーカス操作は調査対象になりました。
ただし、最後に実行したリクエストが記録されておらず、この候補を裏付ける直接の証拠はありません。

### 7.3. その他の待ちと調査範囲

ソケットの送受信待ちも、現行コードから除外できない候補です。
動画処理では[`TakeVideoRecordingResult()`と`CancelVideoRecording()`](../../../agents/windows/video_recording.cpp#L73)が`WaitForSingleObject(..., INFINITE)`を使用しています。
今回その処理が呼ばれていたかは不明です。

## 9. 当初説明したQuick Editの無効化方法

この節は、コンソール版に対して説明した方法の記録です。
第10節のGUI常駐化により、以下の対策を製品へ追加する必要はなくなります。

### 9.1. Console APIによる設定

コードから無効化する場合は、`GetConsoleMode()`と`SetConsoleMode()`を使います。
入力モードから`ENABLE_QUICK_EDIT_MODE`を外し、`ENABLE_EXTENDED_FLAGS`を付けます。
その他のモードは取得した値を維持します。
このフラグの扱いは[SetConsoleModeの公式仕様](https://learn.microsoft.com/en-us/windows/console/setconsolemode)に記載されています。

議論で提示したコード例は次のとおりです。

```cpp
static bool DisableQuickEdit() {
  const auto input = GetStdHandle(STD_INPUT_HANDLE);
  DWORD mode = 0;
  if (!GetConsoleMode(input, &mode)) {
    return false;
  }

  const DWORD updated =
      (mode | ENABLE_EXTENDED_FLAGS) & ~ENABLE_QUICK_EDIT_MODE;
  return SetConsoleMode(input, updated) != FALSE;
}
```

`ENABLE_EXTENDED_FLAGS`の指定が必要です。
標準入力のハンドルに対して設定する点も確認しました。

agent-roverへ組み込む位置としては、[`wmain()`の冒頭](../../../agents/windows/main.cpp#L26)を提案しました。
最初の`PrintAgentVersionBanner()`より前に設定すれば、起動時の出力より先にQuick Editを無効化できます。

このコードは説明用の例です。
当初は、実装する場合に標準入力のリダイレクトやコンソールのない実行環境も考慮する必要があると説明しました。
取得失敗と設定失敗の扱いを決める前にGUI常駐化の方針となったため、この検討は終了します。

## 10. 今回の指示に基づく変更方針

### 10.1. 要件と当初案の扱い

最初の議論では、Quick Editの無効化とファイルへのログ出力を提案しました。
利用者から提案の方向性について了承があり、その後のGUI常駐化で解消する課題を踏まえて再整理する指示がありました。
今回指定された要件は次のとおりです。

| 要件 | 今回の整理 |
| --- | --- |
| システムトレイに常駐 | PEのサブシステムをWindows GUIに変更し、コンソールを作らない |
| トレイメニューからログを参照 | ListViewコモンコントロールによる簡易ビューアーを用意 |
| 表示件数を制限 | 最新1,000件を保持する案とし、それ以前の記録はファイルで参照 |
| ログを収集しやすくする | ビューアーとは独立してファイルへ出力 |
| バージョンバナーとトークンを表示 | ListViewの上に、それぞれ別のコントロールとして配置 |
| ウィンドウをサイズ変更可能にする | 上部の情報欄を確保し、残りの領域にListViewを追従させる |
| Windowsの最低要件を維持 | i686は`_WIN32_WINNT=0x0501`、amd64は`0x0502`を維持 |
| 停止を受付全体へ波及させない | 同期ログ出力、対象アプリ待ち、通信や終了処理の待ちを分離 |

Quick Editの無効化は、この要件に置き換えます。
GUI版では`AllocConsole()`や`AttachConsole()`によるログ用コンソールの作成・接続も行わず、標準出力・標準エラーへログを流す経路を残しません。
PEフラグだけを変え、従来の`printf()`を残して完了とする変更ではありません。

### 10.2. 起動、トレイ、終了

[`agents/Makefile`](../../../agents/Makefile#L28)には現在`-municode`だけがあり、GUIサブシステムの指定はありません。
`-mwindows`を追加し、GUI用のエントリーポイントとメッセージ処理を用意する案です。
`-municode`はUnicode起動コードの選択であり、GUIサブシステムの指定とは別です。
[GCCのMinGWオプション](https://gcc.gnu.org/onlinedocs/gcc/Cygwin-and-MinGW-Options.html)で、それぞれの役割を確認できます。

トレイメニューには「ログを表示」「ログフォルダーを開く」「終了」を設ける案とします。
ビューアーの閉じる操作はウィンドウを隠し、常駐と記録を続けます。
終了操作はトレイメニューから行い、接続の切断、処理の中断要求、ログの保存を期限付きで進めます。
対象アプリの停止やログ保存の遅延によって、終了処理を無期限に待たせません。

初回起動時はトレイへ常駐し、利用者がメニューからビューアーを開いてトークンを参照する案です。
ログ追加時にウィンドウを自動で前面化しません。テスト中のフォーカスを変えないためです。
Explorerの再起動後はトレイアイコンを再登録し、アプリ終了時には削除します。
`TaskbarCreated`の受信には、ブロードキャストを受け取れる隠しトップレベルウィンドウを使用します。
トレイの仕様は[Shell_NotifyIconW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shell_notifyiconw)、再登録は[The Taskbar](https://learn.microsoft.com/en-us/windows/win32/shell/taskbar)を参照します。

引数解析、待受アドレス・ポート、認証トークンの生成という起動時の役割はGUI側へ移します。
`--help`、引数エラー、トークン生成失敗、bind失敗などの表示先も、ヘルプまたはエラーのウィンドウとログへ変更します。
ビューアーを作る前の失敗はエラーダイアログで通知し、表示先がなく失敗理由を参照できない状態を避けます。
待受成功の表示は、実際にlistenが成功してから更新します。

### 10.3. ログビューアー

画面は次の順序とします。バナーとトークンはログ行に混ぜません。

```text
+-----------------------------------------------------+
| agent-rover native windows agent [version-commit]     |
| Copyright / URL / Licence                            |
+-----------------------------------------------------+
| Token: [コピーできる読み取り専用の値                 ] |
+-----------------------------------------------------+
| 時刻 | レベル | 接続・リクエスト | 内容              |
| ...                                                 |
|                  ログListView                       |
+-----------------------------------------------------+
| 待受状態 / ログ保存先 / 保存失敗・欠落の状態          |
+-----------------------------------------------------+
```

[`BuildAgentVersionBanner()`](../../../agents/windows/version_banner.cpp#L26)は文字列生成として再利用し、標準出力へ書く`PrintAgentVersionBanner()`は不要になります。
バナーは複数行のSTATICまたは読み取り専用EDIT、トークンは選択・コピーできる読み取り専用EDITで表示する案です。
認証なしの起動では、トークン欄に認証が無効であることを表示します。
ログファイルの収集でトークンまで共有されないよう、値はこの専用欄だけに表示し、ファイルやイベント行には含めません。
バージョン、起動ID、待受設定はファイルの起動記録にも残します。

ListViewはレポート形式とし、最新1,000件を固定長のリングバッファに保持します。
1イベントを1行として扱い、制御文字や改行は表示前に正規化します。
行数だけではメモリ上限にならないため、1件の文字数とログキューの総バイト数にも上限を設けます。
長すぎるメッセージには省略を明示し、リクエスト本文やバイナリを丸ごと記録しません。

保持データと表示行の対応を単純にするため、`LVS_OWNERDATA`でリングバッファを参照する案です。
`LVN_GETDISPINFO`ではメモリ上のデータだけを返し、ファイル読取りや他の実行主体への同期待ちを行いません。
仮想ListViewの仕様は[About List-View Controls](https://learn.microsoft.com/en-us/windows/win32/controls/list-view-controls-overview)を参照します。
1,001件目からは古い行を取り除きますが、表示から消すこととファイルから削除することは別の処理です。
ビューアーを閉じている間も保持を続け、再表示時は直近の1,000件を表示します。
既存ファイルを読み込む機能や、1,000件を超えて過去へスクロールする機能は今回の範囲に含めません。

ウィンドウはサイズ変更可能とし、`WM_SIZE`で上部の情報欄と下部の状態欄を確保して、ListViewを残りの幅と高さへ配置します。
最小サイズを定め、縮小してもトークン欄やListViewの寸法が負にならないようにします。
既存のDPI対応と古いWindows向けの経路を維持し、最新のDPI APIを必須にはしません。

ログ追加による再描画は一定件数ずつまとめ、連続ログでメッセージ処理を占有しないようにします。
末尾を表示中の場合だけ末尾へ追従し、過去の行を読んでいる間は強制スクロールしません。
選択対象が1,000件の範囲外へ押し出された場合は、行番号の再利用で別の記録を選択したように見えない扱いにします。

### 10.4. ファイル出力と診断項目

ログ発生側は、時刻と識別子を付けた小さなレコードを有界キューへ渡して戻ります。
ファイルへの書き込み完了や、ListViewの更新完了を待ちません。
ビューアー用の保持領域とファイル出力用キューを分け、ウィンドウを隠したりログファイルが書けなくなったりしても、相手側まで停止させない設計とします。
UIへの通知も各ログにつき1個のメッセージを無制限に積まず、更新待ちの通知をまとめます。

出力形式はUTF-8の行単位テキストを基本案とします。
UTC時刻に加え、起動IDと連番を付け、ビューアーとファイルの記録を照合できるようにします。
リクエストについては、接続ID、リクエストID、メソッド、受付・実行開始・完了または失敗、経過時間、処理段階を記録します。
失敗したAPI名と`GetLastError()`または`WSAGetLastError()`も、失敗直後に取得して保存します。
時刻が補正されても経過時間を誤らないよう、UTC表示と所要時間の計測は分けます。
認証トークン、クリップボード本文、入力文字列、ファイル内容は記録対象にしません。

ファイルは追記し、サイズによるローテーションと有限の保存世代数を設けます。
保存先、1ファイルのサイズ、世代数の初期案は、利用者が書き込める`%APPDATA%\agent-rover\logs`、10MiB、5世代です。
これらの数値は、実装段階で確定する運用上の提案です。
多重起動時は起動IDなどでファイルを分け、別インスタンスが使用中のファイルを削除しません。
過去の起動分も整理対象にし、再起動するたびに古いログが無制限に増える設計を避けます。
現在の出力先をビューアーへ表示し、トレイからそのフォルダーを開けるようにします。

ファイル出力には、書き込み以外に作成、ローテーション、削除、flush、closeの待ちもあります。
非同期WriteFileに置き換えるだけで、すべての待ちがなくなるとは扱いません。
非同期化できるI/Oはcardioで完了を待ち、それ以外の停止し得る処理は受付から隔離します。
1行ごとの同期flushは行わず、通常時の書き出し周期と終了時の保存期限を定めます。
OSのキャッシュへ書き出した状態と、強制終了・電源断でも残ることは区別します。

保存先が停止している状況では、有限メモリ、受付の継続、全ログの無欠落を同時には保証できません。
キュー上限に達した場合は発生側を待たせず、欠落した件数と連番の範囲を保持します。
保存失敗や欠落は状態欄に表示し、保存が再開した時に要約を残す案です。
エラー報告を同じ満杯のキューへ繰り返し投入する循環は作りません。
1,000行の表示上限、ファイル待ちキューの上限、ディスク上の保存上限は、それぞれ別に管理します。

## 11. 接続受付を止め得る箇所の洗い出し

次の表は現在の製品コードを調査した結果です。
「待ちがある」というコード上の事実と、「今回その場所で停止した」という未確認の推測を区別します。
優先度Aは受付全体への波及を防ぐための基盤変更、優先度Bはその後に個別操作の待ちと回復を改善する対象です。
優先度Bの処理も、基盤変更の段階から受付経路の外に置きます。

### 11.1. 受付、通信、ログ

| 優先度 | 現在の箇所 | 停止・滞留の経路 | 改善方針 |
| --- | --- | --- | --- |
| A | [`RunTcpServer()`](../../../agents/windows/tcp_server.cpp#L387) | `HandleClient()`が戻るまで次の`accept()`へ進まない。アイドル接続だけでも後続の認証が待つ | 接続ごとの状態を分け、受付・認証・各接続のI/Oをイベント駆動で進める |
| A | [`ReceiveExact()`、`SendAll()`](../../../agents/windows/frame.cpp#L46) | 認証応答、途中までのフレーム、受信しない相手への送信で同期的に待つ。期限がない | 非ブロッキングI/O、部分受信・部分送信の状態管理、認証・フレーム・送信期限、有界送信キュー |
| A | [`HandleFrame()`](../../../agents/windows/tcp_server.cpp#L207)、[`HandleJsonRequest()`](../../../agents/windows/json_protocol.cpp#L1100) | JSONの全操作を同期実行し、Ping・Closeもその後になる | フレームの処理と操作の実行を分離し、操作待ち中も切断と生存確認を処理する |
| A | [`CapabilitiesJson()`](../../../agents/windows/json_protocol.cpp#L487)、[`IsVideoCaptureSupported()`](../../../agents/windows/win32_video.cpp#L617) | readyやcapabilitiesの生成時にもMedia FoundationのDLLを同期でロード・解放する | 機能検出を受付から分けて結果を保持し、認証後の応答経路で毎回ロードしない |
| A | [`PrintAgentLogEvent()`](../../../agents/windows/agent_log.cpp#L130) | リクエスト・受付の経路で`printf()`と`fflush()`が待つ | 第10.4節の有界キュー、表示と保存の分離。ログロックをI/O中に保持しない |
| A | [`SendBinaryFile()`](../../../agents/windows/tcp_server.cpp#L76) | ファイル読取りとソケット送信を繰り返し、接続の処理を占有する | 分割した非同期読取り・送信。送信待ちを他接続へ波及させず、メモリ量と転送寿命を制限 |
| B | [`ResolveHost()`](../../../agents/windows/tcp_server.cpp#L30)、起動処理 | ホスト名指定時の`gethostbyname()`や初期化が起動時に待つ | GUIのメッセージ処理を止めずに初期化し、失敗・準備中・待受中を区別。既定の数値アドレスで必ず起きる問題ではない |

`listen()`のバックログを増やしても、接続後の処理が直列である問題は解決しません。
同様に、`SO_RCVTIMEO`だけを加えても、対象アプリの待ちや、遅い相手が少量ずつ送るフレーム全体の期限は管理できません。
認証前の接続数、接続全体の数、未処理リクエスト数、フレームとバイナリ転送の総量も制限対象です。
[`BinaryTransferStore`](../../../agents/windows/binary_transfer.h#L67)は接続単位の蓄積先ですが、複数接続化後はサーバー全体の上限も必要になります。

### 11.2. 対象アプリやOS機能を待つ操作

| 優先度 | 現在の箇所 | 停止・滞留の経路 | 改善方針 |
| --- | --- | --- | --- |
| B | [`ActivateWindow()`、`ShowWindowById()`](../../../agents/windows/win32_windows.cpp#L216) | `ShowWindow()`、前面化などが対象側の処理と同期する可能性 | `ShowWindowAsync()`等を候補とし、操作の要求と状態の確認を分ける。受付の実行主体から直接呼ばない |

| A | [`TakeVideoRecordingResult()`、`CancelVideoRecording()`](../../../agents/windows/video_recording.cpp#L73) | 録画スレッドを`INFINITE`で待つ。切断後の後始末も次の受付を止める | 完了HANDLEを非同期で待つ。中断・終了期限を設け、回収中でも受付を続ける |

| B | [`ReadFileBytes()`、`WriteFileBytes()`、manifest](../../../agents/windows/win32_files.cpp#L116)、[`win32_cleanup.cpp`](../../../agents/windows/win32_cleanup.cpp#L87) | 同期I/O、全体読込み、ディレクトリ再帰、ACLの修復・削除。遅い保存先では長時間化する | データ転送は非同期化・分割し、同期メタデータ操作は隔離。削除範囲や所有ディレクトリの検証を維持 |
| B | [`ReadEventLogs()`](../../../agents/windows/win32_eventlog.cpp#L104) | 同期`ReadEventLogW()`を繰り返す。返却件数の上限は走査量や所要時間の上限ではない | 受付から隔離し、走査量と期限を管理。途中で打ち切った結果を完全な結果として返さない |
| B | [`CaptureScreenRect()`](../../../agents/windows/win32_capture.cpp#L88)、[`png_encoder.cpp`](../../../agents/windows/png_encoder.cpp) | 画面取得、画像変換・圧縮により長時間占有する可能性 | 解像度・データ量を制限し、重い処理を受付から分離。`PrintWindow()`待ちという原因には置き換えない |

Windows APIの代替には意味の違いがあります。
[`ShowWindowAsync()`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showwindowasync)は表示変更の要求を非同期で渡します。
[`SWP_ASYNCWINDOWPOS`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos)も、異なる入力キューに属する場合に要求を投稿する指定です。
どちらも、対象アプリが変更を完了したことや、その要求を後から取り消せることを保証するものではありません。
既存APIが返すウィンドウ状態との整合は、通知と期限のある状態確認で扱います。
入力キューを結合したまま非同期指定に頼る案にはしません。

クリップボードの遅延レンダリングは、[Clipboard Operations](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-operations)に記載された所有者とのやり取りを指します。
一方、現行の[`window.close`](../../../agents/windows/win32_windows.cpp#L378)は`PostMessageW(WM_CLOSE)`で要求しています。
すでに非同期の箇所まで一律に同期呼び出しと分類しません。
[`GetWindowTextW()`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowtextw)も、自プロセスのウィンドウと他プロセスのキャプションでは取得方法が異なります。
列挙・snapshotのすべてが対象アプリへの同期メッセージになるとは判断していません。

### 11.3. 複数接続化と終了処理で併せて直す箇所

| 現在の箇所 | 複数接続化で必要になる対応 |
| --- | --- |
| [`g_managed_processes`とID採番](../../../agents/windows/win32_process.cpp#L40) | 操作を所有する実行主体、IDの範囲、同時releaseとsnapshotの順序を定義。接続終了時に他接続のプロセスを解放しない |
| [`capture_directories`](../../../agents/windows/win32_cleanup.cpp#L24) | 作成・検証・削除を同じ所有者で管理し、同時操作で検証情報を壊さない |
| [`CreateApplicationProcess()`の標準HANDLE継承](../../../agents/windows/win32_process.cpp#L278) | リダイレクトしないストリームを親の`GetStdHandle()`から補う実装を見直す。GUI版で親の標準HANDLEがなくても、子の起動・片側だけのリダイレクト・stdout/stderr取得を成立させる |
| [`BinaryTransferStore`と`VideoRecordingStore`](../../../agents/windows/tcp_server.cpp#L305) | 接続単位の寿命を維持し、切断後の非同期処理から解放済み領域へアクセスさせない |
| [`CurrentLogTimestamp()`](../../../agents/windows/agent_log.cpp#L13) | 複数実行主体からの利用を考慮し、共有される時刻変換結果や出力状態を無保護で扱わない |
| [`HandleClient()`の後始末](../../../agents/windows/tcp_server.cpp#L328)、一時動画削除 | 無期限の録画待ちや遅いファイル削除を、接続状態の解放と次の受付の前提にしない |
| [`createPendingRequestTable()`](../../../agent-rover/src/protocol.ts#L655)、[`request()`](../../../agent-rover/src/driver/connection.ts#L2022) | クライアントのTIMEOUT、サーバーへの中断要求、実処理の中断完了を区別。送信待ちも期限の対象とする |
| [`transport.close()`](../../../agent-rover/src/driver/transport.ts#L260) | `socket.end()`後のclose待ちに終了期限を設け、送信や相手の切断が進まない場合の回収経路を用意 |
| [`AuthenticateClient()`](../../../agents/windows/tcp_server.cpp#L161) | 認証前のClose・EOF・期限切れをトークン不一致と区別。形式エラーの改善を受付停止の修正と取り違えない |

共有状態を大きなmutexで保護し、そのまま対象アプリやファイルを待つと、別接続も同じmutexで止まります。
単に接続ごとにスレッドを増やす方法では、待ちの波及と資源の上限を管理できません。
状態の所有者を決め、必要な順序だけをキューで保つ設計が必要です。

標準HANDLEの継承は、GUI化が既存機能へ与える影響として確認する項目です。
コンソールを持たない親での`GetStdHandle()`の扱いは[公式仕様](https://learn.microsoft.com/en-us/windows/console/getstdhandle)を参照します。
必要な子プロセス用HANDLEを明示して渡し、エージェントにログ用コンソールを再作成して回避する方法は採りません。

## 12. 待ちを受付から分離する設計案

### 12.1. 実行の境界と共有状態

提案する構成では、次の役割を分けます。役割の数だけスレッドを作るという意味ではありません。

| 役割 | 所有する状態と責務 | その経路で待たせない処理 |
| --- | --- | --- |
| 受付・通信 | listener、認証、接続、フレーム、送信キュー、期限、軽量なcapabilitiesとPing | 操作の完了、ファイル保存、UI描画 |
| 操作の実行 | ウィンドウ操作、入力、クリップボード、プロセス・ファイル・動画の作業 | 他の接続の受付・認証を前提とした同期待ち |
| ログの収集・保存 | レコードの採番、有界キュー、ファイルとローテーション | 発生側を待たせる書き込み、無期限flush |
| GUI | トレイ、バナー、トークン、直近ログ、状態表示 | 対象アプリへの同期メッセージ、接続処理、ファイル読取り |

I/Oはcardioを基盤にしたイベント駆動とし、接続ごとの受信・送信・操作待ちを別の状態として管理します。
同期関数をcoroutineの中で呼ぶだけでは非同期化にならないため、`HandleJsonRequest()`全体をそのまま通信の継続処理へ移すことはしません。
操作が止まっても、別接続は認証を完了してcapabilitiesや生存確認へ応答できることを基準にします。
`accept()`が戻るだけで改善済みとは判断しません。
capabilitiesの生成には、あらかじめ完了した機能検出の結果を使います。
検出が失敗した機能の扱いを定め、接続のたびにDLL読込みを行う現在の経路を残さないようにします。

同一デスクトップへのフォーカス・入力・クリップボード操作は順序が結果を変えます。
これらには直列の実行キューを設け、異なる接続の入力を途中で混ぜません。
そのキューが埋まった場合は、操作を期限付きで待たせるかbusyを返し、受付や認証まで待たせません。
同一接続の状態変更リクエストの順序、バイナリの転送IDとチャンク順序、同一socketへの書込みの直列化も維持します。
同じ接続への大きな転送で応答が詰まる場合は、その接続の送信期限で解決し、別接続には波及させません。

同期APIに安全な中断方法がない処理は、受付を担うプロセスから補助プロセスへ隔離する案を優先します。
補助プロセスとのIPCも非同期で扱い、同時実行数、待ち行列、回収中の件数を制限します。
期限を過ぎるたびに新しい補助プロセスを無制限に起動する設計にはしません。
`TerminateThread()`で止めたり、完了していない処理のcontextを解放したりして回復したことにしません。

補助プロセスの再起動時には、その処理が所有する一時ファイルやHANDLEの回収を行います。
managed process、Job、capture directoryは所有者を明示し、補助プロセスの停止で他接続の資源や対象アプリまで意図せず終了させない設計とします。
既存のkill-on-releaseなどの明示された意味は維持します。
非同期化できる処理はこの境界から徐々に移せますが、中断できない処理を通信側へ戻さないことが条件です。

### 12.2. 期限切れと中断

認証の期限、フレーム受信の期限、送信の期限、操作の期限、終了・回収の期限を分けます。
操作の期限には実行待ち時間も含め、少量の受信や再試行のたびに無制限に延長しません。
録画など正当に時間のかかる処理では、要求された時間と処理内容を考慮し、全操作を一律30秒で打ち切る設計にはしません。

まだ開始していない操作は、期限切れや切断時にキューから除きます。
開始済みの操作には中断を要求しますが、「待機を打ち切った」と「OSの操作が中断した」は別の状態です。
遅れて届く完了通知を別のリクエストへ対応付けたり、切断後のsocketへ送信したりしません。
すでに対象アプリへ渡した操作には、タイムアウト後も副作用が起こり得ます。その場合に取消完了と報告しないようにします。

クライアントのタイムアウトをサーバーへ伝える方法と、サーバー固有の最大実行時間を定めます。
リクエストの期限・取消をプロトコルへ加える場合は、TypeScript側とWindows側を同じ段階で変更し、プロトコル版も更新します。
後方互換のために旧経路を残すことは、今回の前提に含めません。

### 12.3. GUIメッセージ処理との関係

GUIのメニュー表示中、ウィンドウ移動・サイズ変更中にも、通信と期限の処理が進むことを確認します。
通常の外側のメッセージループだけで非同期処理を進めると、Windowsのモーダルなメッセージループに入った間、処理が進まなくなる可能性があります。
GUIと通信を同じdispatcherで動かす場合は、cardioの`dispatcher_host_win32_auto`など、内側のメッセージループでも配送される公開APIを検証します。
別のdispatcherを使う場合も、UIへの反映は非同期の通知とし、互いに同期呼び出しで待つ経路を作りません。
実行主体の配置は次節の互換性検証で確定します。

## 13. Windows最低要件と非同期基盤の確認事項

### 13.1. GUIで新たに使う機能

現在の`_WIN32_WINNT`値とMinGWの固定ツールチェーンを維持します。
GUI化によってOS要件をVista以降へ引き上げません。
基本的なトレイ、EDIT・STATIC、レポート形式のListViewで実装し、最新WindowsだけのUI機能は必須にしません。

`Shell_NotifyIconW()`はXPで利用できる通知形式を使い、`NOTIFYICONDATAW.cbSize`もXPに対応するサイズを選びます。
`NOTIFYICON_VERSION_4`やGUIDによるアイコン識別を前提にせず、`hWnd`と`uID`による識別を基本案とします。
構造体サイズと各フィールドの対応OSは[NOTIFYICONDATAW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-notifyicondataw)で確認できます。
ListViewの初期化には`InitCommonControlsEx()`を使用する案です。
トレイとコモンコントロールの導入では、`shell32`と`comctl32`のリンク、および必要なリソースを追加します。
コントロールの初期化と旧OSでの利用範囲は、[InitCommonControlsEx](https://learn.microsoft.com/en-us/windows/win32/api/commctrl/nf-commctrl-initcommoncontrolsex)と[Common Control Versions](https://learn.microsoft.com/en-us/windows/win32/controls/common-control-versions)を参照します。

[`windows-toolchain.test.mjs`](../../../agents/tests/windows-toolchain.test.mjs#L77)は、現在リンクを許可するDLLと、XPより後のAPIがimportされていないことを検査しています。
このテストは新たな2つのDLLを現在許可していません。
GUI化で必要になるDLLを許可する変更と、OS要件を超えるAPIを検出する検査の維持を併せて行います。
PEヘッダーのGUIサブシステムとOS・サブシステムのバージョンも両アーキテクチャで確認します。
プリプロセッサの値だけを維持してXP対応を確認したことにはしません。

### 13.2. cardio導入前に解決する制約

現在のagent-roverにはcardioの依存定義がありません。
調査では隣接するcardioのチェックアウト、コミット`e2cc7478c7f3efffac963dcf5d4a51bbeea3f3a7`のREADMEと公開APIコメントを読みました。
参照元は[公式README](https://github.com/kekyo/cardio/blob/e2cc7478c7f3efffac963dcf5d4a51bbeea3f3a7/README_ja.md)と[公開ヘッダー](https://github.com/kekyo/cardio/blob/e2cc7478c7f3efffac963dcf5d4a51bbeea3f3a7/include/cardio.h)です。

`from_win32_handle()`でHANDLEの完了を待ち、`dispatcher_host_win32`でメッセージと待機を統合する公開APIが用意されています。
ただし、導入すれば現在のビルド条件のまま利用できるとは、まだ確認できていません。

| 調査で分かったこと | 導入前の確認 |
| --- | --- |
| `win32`補助関数やIOCPの中断処理に`CancelIoEx()`の直接呼出しがある | XPで使えないAPIの宣言・importが入らない構成と利用版を確認。補助関数を呼ばなければ必ず解決するとは仮定しない |
| `GetQueuedCompletionStatusEx()`には`_WIN32_WINNT`による分岐がある | 一部の分岐だけを根拠にライブラリ全体のXP対応を判断しない |
| 現在のエージェントは`-fno-exceptions`でビルド | 取消付き公開オーバーロードには例外有効時だけのものがある。利用可能なAPIとエラーの受け渡しを確認 |
| 固定ツールチェーンはGCC 12のwin32スレッドモデル | cardioが使うC++標準のスレッド・同期機能をビルドでき、実行時にも最低OS要件を保てるか確認 |
| HANDLE待機には同時待機数の上限がある | listener、接続、ファイル、通知用HANDLEを合算し、受付上限を設計する |
| `from_win32_overlapped()`の取消は待機の取消で、ネイティブI/Oの取消ではない | buffer、OVERLAPPED、HANDLEはネイティブ完了まで保持。待機の終了だけで解放しない |

[`CancelIoEx()`](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelioex)の最低クライアント要件はVistaです。
XPで利用できる[`CancelIo()`](https://learn.microsoft.com/en-us/windows/win32/api/ioapiset/nf-ioapiset-cancelio)は、呼出しスレッドが発行したI/Oだけを対象にします。
名前を単純に置換する方法では同じ中断動作になりません。
I/Oを開始する実行主体と中断する実行主体、同じHANDLE上の別操作への影響を設計します。

socketには、XPで使える非ブロッキング通知とcardioのHANDLE待機を組み合わせる案があります。
候補の[`WSAEventSelect()`](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-wsaeventselect)はsocketを非ブロッキングモードにし、受付・読取り・書込みなどの通知を扱えます。
ただし、これを採用するかIOCPを使うかは、上記の制約を含む小さな実行可能プログラムで確認してから決めます。
外部ライブラリの内部APIやベンダーコードの書換えで回避したり、OS最低要件を上げたりする案にはしません。
利用可能な公開API・依存版で要件を満たせない場合は、その依存条件を記録して計画を見直します。

### 段階2. GUI常駐と独立した接続受付を備えたエージェント

### 段階4. 個別操作の中断・回収を改善

成果物は、対象アプリ、動画、ファイルなどの遅延が起きても、期限と回収結果を確認できるエージェントです。

ウィンドウ操作の完了の意味、入力の順序、DPI座標、managed processとcapture directoryの所有権は回帰テストで確認します。

完了条件は、各処理を止めるテストで他接続が応答し、該当操作が定義された失敗または取消結果になり、回収処理も期限を超えて全体を待たせないことです。

期限切れで除かれた未実行操作が後から対象アプリへ適用されないことも検証します。

### 段階5. クライアントとの整合と全体検証

成果物は、新しい終了・期限の動作に対応するTypeScriptドライバー、更新した利用者向け文書、配布可能なWindows実行ファイルです。

| 中断と終了 | 動画・操作・保存が未完了でも終了経路が無期限待ちにならず、中断要求と実際の完了を区別する |
| 資源と順序 | 接続間の状態混同、入力順序の破壊、解放済み領域の参照、回収対象の無制限な増加がない |
| Windows要件 | i686の`0x0501`、amd64の`0x0502`、固定ツールチェーンとPEの要件を維持。新しい必須API・DLLで最低OSを引き上げない |
| 回帰 | 既存の認証、操作、ファイル、画像・動画、DPI、managed cleanup、配布のテストを含む全体テストが通る |

停止を検証するテストでは、テスト対象が所定の待ちに入ったことをイベントや通信で確認し、その待ちを解除する前に別接続の完了を検証します。
短いSleepの後に成功していればよい、という時間依存の判定にはしません。
タイムアウト自体のテストでは時計や通知を制御できる境界を使い、統合テストの上限時間は停止検出のために別途設けます。
UIは実ウィンドウの操作とサイズ変更で検証し、コードにコントロール名が書かれているだけで合格としません。

## 19. 段階2の実施結果（2026年10月3日）

### 19.1. GUIと接続処理

両実行ファイルをGUIサブシステムへ変更しました。バナーとコピー可能なトークン欄をListViewの上に分けて配置しています。
ListViewは最新1,000件を参照し、ウィンドウのサイズ変更に追従します。閉じる操作では非表示になり、トレイの「Show logs」で再表示できます。
トレイの「Exit」は受付を止め、各接続と補助プロセスを期限付きで終了させます。Explorerの再起動通知によるアイコンの再登録も実装しました。
起動時のヘルプとエラーはダイアログへ表示します。バナーやイベントをコンソールへ書く処理は取り除きました。

GUIと通信は`dispatcher_host_win32_auto`で動きます。
socketには`WSAEventSelect()`を使用し、1 socketにつき1つのHANDLE待機から、読取り・書込みの継続処理へ通知します。
部分受信・部分送信を扱い、認証は10秒、フレーム全体の受信と送信は30秒を上限としました。
認証後のアイドル時間はフレーム受信時間に含めず、最初の1バイトを受け取ってからフレーム全体の期限を計測します。

接続ごとに操作用の補助プロセスを所有し、名前付きパイプのI/Oをcardioで待機します。
capabilities、Ping、Closeは操作待ちキューを通さず、GUI側で扱います。
ホスト名の解決と動画機能の検出も起動用の補助プロセスで行い、検出結果を認証とcapabilitiesの応答で再利用します。
起動用の補助プロセスは検出後に終了します。

接続数は認証前を含めて16、操作用の補助プロセスは8を上限としました。
要求と応答の各キューは、接続ごとに64件・32MiB、サーバー全体で各64MiBです。
受信中のフレームも別途合計64MiBまでとし、処理済みのバイナリ転送を含めて補助プロセス内の蓄積を16転送・64MiBに制限しました。
上限を超えた接続を終了して、他の接続の受付を続けます。

ウィンドウ、入力、クリップボード、アプリ起動には、デスクトップ単位の実行順序を設けました。
IPC待機を取り消しただけでは、その順序を次の操作へ渡しません。
補助プロセスの実際の終了を確認してから次へ進み、回収期限を超えた補助プロセスは使用枠を保持したまま隔離します。
この場合は、新しい補助プロセスを無制限に作って置き換えません。

### 19.2. 所有権とGUI化に伴う修正

managed processのID、Job、capture directory、バイナリ転送、動画の状態は、接続が所有する補助プロセス内で管理します。
同じ数値のmanaged IDであっても、別接続の状態を操作することはありません。
`killTreeOnRelease: true`のJobには`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`を設定し、補助プロセスを失った場合にも指定された終了方針を適用します。
`false`の場合にはこの指定を追加しません。[Jobの終了条件](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information)を参照してください。
一時ディレクトリの回収や個別操作の期限は、段階4でさらに改善します。

GUI親プロセスの標準HANDLEを子プロセスへ流用すると、Windows 11で片側リダイレクト時の標準入力が無効になることを再現しました。
リダイレクト時は、指定されていないストリームへ継承可能な`NUL`のHANDLEを渡すように変更しました。
補助プロセスのIPC用HANDLEには、起動した対象アプリが継承できない設定を行います。
構成の根拠は[標準入出力をリダイレクトした子プロセスの作成](https://learn.microsoft.com/en-us/windows/win32/procthread/creating-a-child-process-with-redirected-input-and-output)です。

固定GCC 12では、非自明なメンバーを含む一時オブジェクトを`co_await`の引数へ直接構築した箇所で、Windows 11上の起動時にヒープ破損を再現しました。
IPCメッセージをローカル変数として構築してから渡す形に変更し、同じ起動・通信試験が成功しました。
同種の問題の追跡先として[GCC PR107288](https://gcc.gnu.org/bugzilla/show_bug.cgi?id=107288)があります。
コンパイラ更新やcardioヘッダーの変更は行っていません。

## 20. 段階3の実施結果（2026年10月3日）

### 20.1. ファイル保存と診断項目

保存先は`%APPDATA%\agent-rover\logs`です。ビューアーの状態欄に保存中のファイル名を表示し、トレイの「Open log folder」でフォルダーを開けます。
ファイル名には起動時刻とPIDから作ったセッション識別子と世代番号を含めます。
レコードはUTC時刻、セッション識別子、画面と共通の連番、イベントの順でUTF-8へ保存します。
バナーのバージョンも起動ログへ含めます。認証トークンは専用コントロールに表示し、ファイルログへ転記しません。

リクエストは接続ID、リクエストID、メソッド、受信、実行開始、成功・失敗、実行終了、送信開始・完了を記録します。
経過時間には単調時計を使います。構造化されたOSエラーにはAPI名とエラー番号も残し、入力本文や応答本文は記録しません。
操作完了と応答送信完了を分けたため、操作の待ちと送信の待ちを区別できます。

| 項目 | 確定した値・動作 |
| --- | --- |
| メモリ表示 | 最新1,000件、1レコード最大4,096 UTF-8バイト |
| 保存キュー | 最大4,096件かつ4MiB。超過した新規レコードを欠落として数える |
| 書出し | 通常100ms単位でまとめ、1バッチ最大64KiB |
| ローテーション | 1ファイル最大10MiB、通常は5ファイル。別インスタンスの使用中ファイルは削除しない |
| 保存確認 | IPCの各要求は5秒。失敗したバッチは未確認として扱う |
| 再試行 | 補助プロセスの終了確認後、5秒間隔。回収できない場合は置換を止める |
| 正常終了 | 保存とflushは2秒まで待ち、その後は補助プロセスの終了・回収期限を適用する |

欠落・未確認の件数と連番範囲を状態欄へ表示し、保存再開後のファイルにも残します。
書込み済みでも応答を失った場合があるため、「未確認」を必ず未保存とは断定しません。
他インスタンスが使用中のファイルは保持するので、同時起動時の総数は5を超えることがあります。
ローテーション時の列挙も4,096件までとし、削除不能の旧ファイルを無視して新しいファイルを増やし続けません。

ファイルの作成、列挙、削除、flush、Explorer起動は、通信とGUIから隔離したログ用補助プロセスで実行します。
実データの書込みはcardioの公開`win32::write()`で待機し、バッファーとHANDLEを完了まで保持します。
非同期書込みでも保存装置側の条件で待ち得るため、プロセスの境界と期限も設けました。
根拠は[WriteFileの非同期I/Oとバッファー寿命](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-writefile)です。

### 20.2. 検証結果

保存キューの上限と欠落範囲を検証するテストは、実装前に失敗し、実装後に成功しました。
実ファイルの試験では60MiBを超えて書き込み、10MiBでの世代切替、5ファイルへの削減、別の使用中ファイルの保持、UTF-8と書込み位置、保存先エラーを両アーキテクチャのWineで確認しました。

Windows 11ではログ用補助プロセスをデバッガーの方法で停止させ、同一・別接続のcapabilities、別接続の認証、GUIのサイズ変更と再表示を実行しました。
それらの完了後にも補助プロセスが停止中であることを確認してから再開しています。
これは製品の同期方法ではなく、[SuspendThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-suspendthread)を使った試験専用の障害注入です。

1,005回のcapabilities要求を送り、終了後のファイルで1,000行を超える履歴、最初の連番、バージョン、受信・送信・経過時間、終了記録を確認しました。
この試験は診断ログの追加前に行数不足で失敗し、追加後に成功しました。
試験用トークンがどのログにも含まれないことも確認しています。
さらにAPPDATAを通常ファイルへ向けて保存を失敗させ、失敗表示、通信、GUI操作、期限内の終了が機能することを確認しました。

## 21. 段階4の実施記録（2026年10月3日）

### 21.1. 接続の終了と一時領域の回収

段階3の実行ファイルで、標準出力を保存したmanaged processの終了後に接続を閉じても、一時ファイルが残ることを再現しました。
補助プロセス内だけで所有権を管理する構成では、補助プロセスの終了と同時に回収情報も失われます。
これを踏まえ、接続ごとの一時領域を作り、そのパスとネイティブ識別子を親へ通知する構成へ変更しました。
managed captureと動画の出力はその領域内へ置きます。対象アプリへ渡すTEMP・TMPは変更しません。

親は操作用プロセスの終了を確認してから、回収専用の補助プロセスへ所有情報を渡します。
回収側ではvolume serialとfile indexを照合し、既存の所有権・reparse point・アクセス権検査を通して削除します。
パスだけを根拠に削除せず、別のディレクトリへ置き換わっていれば失敗とします。
識別の根拠は[GetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileinformationbyhandle)です。

回収IPCは3秒で打ち切り、その補助プロセスにも有限の終了期限を適用します。
回収に失敗した場合や所有情報を取得できなかった場合は、使用枠を返却せず隔離します。
回収不能の一時領域を残したまま無制限に再作成しないためです。
使用中のファイルを持つ`killTreeOnRelease: false`のアプリも、この条件に含まれます。アプリの終了方針は変更しません。
1接続内で登録できるcapture directoryも、親領域を含めて128件に制限しました。

Windows 11で同じ切断試験を再実行し、接続終了後の一時ファイルの消失を確認しました。
トレイからの終了、保存不能時の終了、停止した対象アプリからの復帰の試験も成功しています。
個別操作の期限と、動画・I/Oの待機方法については、次の作業で検証します。

### 21.2. 操作の期限とI/O・録画の待機

操作の上限は、ウィンドウ・入力・クリップボードが30秒、それ以外が120秒です。
`video.result`には、要求された録画時間と後処理用の120秒を割り当てます。録画時間は最大600,000msとしました。
いずれも要求を受け取った時点から測り、デスクトップの実行待ちを理由に期限を延ばしません。
バイナリ操作が期限切れになった接続は、途中の転送状態を継続利用しないため終了します。

通常のファイル読み書きを、補助プロセス内でcardioのoverlapped I/Oへ変更しました。
バッファーとファイルは、取消を含む実際のI/O完了後まで保持します。
ファイル作成やメタデータ、ハッシュ計算、再帰的削除などの同期処理は、引き続き期限付きの補助プロセスへ隔離しています。
1回の全量読取りは64MiB、directory entryとmanifestは8,192件、manifestの深さは32段までです。
manifestのハッシュはストリームで計算し、ファイル全体を一時的に複製しません。
managed processは1接続64件、イベントログは1回1,000件、イベント受信バッファーは1MiBを上限としました。

文字入力の間隔はSleepからcardioのタイマーへ変更し、同一操作内の文字順序を維持しました。
動画スレッドの完了もcardioのHANDLE待機で扱い、取消は200msで戻ります。
コーデックがその間に終了しない場合はcontextとHANDLEを保持し、親による補助プロセス終了で回収します。
`TerminateThread()`や、動作中のcontextの解放は使用していません。

ShowWindow、MoveWindow、フォーカス、クリップボードは、期限付き隔離の対象として維持しました。
単に`ShowWindowAsync`や`SWP_ASYNCWINDOWPOS`へ替えると、「適用後のsnapshotを返す」という現在の完了条件を満たしません。
これらの非同期APIは要求を対象スレッドへ送るだけで、適用済みを保証しないためです。
対象アプリへ既に渡った要求は、補助プロセスの終了後に副作用が生じる場合があり、取消完了とは報告しません。
参照先は[ShowWindowAsync](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-showwindowasync)と[SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos)です。

64MiBを超えるファイルを読み込んでしまう旧動作と、停止したコーデックの取消が戻らない旧動作をテストで再現しました。
修正後は両アーキテクチャのWineで、容量制限、バイナリの読み書き、取消後の寿命保持、実終了後の解放を確認しました。
待機時間を数値で与える期限ポリシーのテストでは、期限を過ぎたキュー内操作の残時間がゼロとなることを確認しています。
Windows 11統合試験は3ファイル・5件が成功しました。実際の録画、DPI、managed cleanup、所有権を偽った回収の拒否、ファイルI/O、対象ウィンドウの停止を含みます。

### 21.3. 公開動作の補足

Windowsエージェントはトレイから操作します。バージョン・トークンは専用欄、直近の記録はListView、過去の記録はファイルで参照します。
クライアントの要求期限が過ぎた場合は、その接続全体を終了し、未実行の操作を破棄します。
同じ接続の他の待機要求も失敗するため、継続する場合は再接続します。
実行済みの入力や対象アプリ側の副作用まで取り消す保証はありません。
この動作と第20節のログ収集方法を、日本語READMEを原本として英語版と配布版へ反映します。
