# Building from source

## Linux build host

Use an x86-64 Linux host with Bash, GNU Make, Node.js/npm (see the package engine
requirements), and working rootless Podman. Install missing host tools using your
distribution's package manager. Host MinGW packages are not needed.

From the repository root:

```sh
npm ci
./prereq.sh
npm run build
npm test
```

`prereq.sh` builds the Windows toolchain image on its first run. Later runs reuse
the prepared image. The initial build needs registry and Debian snapshot network
access. Normal compilation uses the local image with networking disabled and does
not download or rebuild it automatically. If the image is missing, the build asks
you to run `prereq.sh`.

Windows agents are written to `agents/dist/agent-amd64.exe` and
`agents/dist/agent-i686.exe`. `make -C agents -j4` also uses the pinned image.
`make -C agents clean` removes build outputs without removing the image.
`npm run pack --workspace agents` creates the Windows distribution archive.

## Toolchain pinning

[The Containerfile](agents/toolchain/Containerfile) pins the Debian base image by
digest and uses a dated [Debian snapshot](https://snapshot.debian.org/#Usage) for
all package dependencies. The cross toolchain is GCC 12.2.0 with the Win32 thread
model, MinGW-w64 10.0.0/MSVCRT, and binutils 2.40. Both Windows architectures use
this definition. Host compiler updates do not change these builds.

The Containerfile content hash identifies the local image. After an intentional
toolchain definition change, run `./prereq.sh` again; Make rebuilds affected
objects. Old images remain available until explicitly removed. To show the
current image name:

```sh
./agents/scripts/windows-toolchain.sh --image
```

Make and npm run on the host. Version information is generated by the existing
`screw-up format` step on the host; compilers, resource compilers, linkers, and PE
inspection tools run in disposable containers. Containers retain the host user's
file ownership and mount the checkout at the same absolute path. The desktop and
cleanup integration fixtures use the same toolchain as the agents.

Custom `OBJ_ROOT`, `GENERATED_DIR`, and output paths should be inside the checkout.
To use a directory outside it, create that directory and export
`AGENT_ROVER_BUILD_DIR` with its absolute path; the launcher additionally mounts
that directory. For example:

```sh
mkdir -p /tmp/agent-rover-build
AGENT_ROVER_BUILD_DIR=/tmp/agent-rover-build make -C agents -j4 \
  OBJ_ROOT=/tmp/agent-rover-build/obj \
  GENERATED_DIR=/tmp/agent-rover-build/generated \
  TARGET_ROOT=/tmp/agent-rover-build/dist
```

Explicit overrides of `AMD64_CXX`, `I686_CXX`, `AMD64_RC`, or `I686_RC` bypass the
default toolchain selection and require separate compatibility validation.
See [Podman build](https://docs.podman.io/en/v4.9.3/markdown/podman-build.1.html)
and [Podman run](https://docs.podman.io/en/v4.9.3/markdown/podman-run.1.html) for
image storage and rootless volume behavior.

## Validation

Run `npm test` for the complete suite. Native build tests inspect the actual PE
imports of both agents: only the expected system DLLs may be required, and known
post-XP imports such as `GetThreadId`, newer synchronization APIs, and modern DPI
queries must not appear as mandatory imports. The tests also check that setup
reuses the image and that a changed definition requires preparation.

For Windows integration tests, configure `AGENT_ROVER_WIN11_HOST` and
`AGENT_ROVER_WIN11_TOKEN` for an interactive Windows 11 machine running the
bootstrap agent (0.4.0 is supported), then run the same `npm test` command. The
tests deploy the freshly compiled agents and exercise placement, DPI, recording,
and process/file cleanup. The Windows firewall must allow the test ports 39407,
39408, and 39417 from the test driver's host. Without those environment variables,
the Windows integration tests are skipped.

The targets remain Windows XP SP2 for i686 and Windows XP Professional x64
Edition for amd64. Static import inspection is a regression check, not proof of
complete XP compatibility. An XP machine is still required to validate startup,
authentication, and basic operations with its actual system DLLs. Windows 11
integration results do not establish XP runtime compatibility.

The original runtime regression involved
[`GetThreadId`, available from Vista](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadid).
GCC's [Win32 threading implementation changed in GCC 13](https://gcc.gnu.org/gcc-13/changes.html).
Keep the import checks and XP runtime validation when updating the pinned tools.
